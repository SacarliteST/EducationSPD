# Концепция EducationSPD

## Часть 1. Навыки и учебные наблюдения

### 1. Назначение документа

Этот документ фиксирует предметную модель системы поддержки принятия решений
EducationSPD. Система предназначена для оценки предполагаемой степени освоения
навыков и формирования рекомендаций на основании результатов учебной деятельности.

EducationSPD проектируется как самостоятельный сервис платформы и не зависит от
предметной области одного учебного модуля. SQL Module является первым источником
наблюдений, но та же модель должна применяться к модулям программирования,
математики, тестирования и другим видам учебной деятельности.

В первой части определены:

- понятие навыка;
- виды навыков;
- учебный эпизод и условия его завершения;
- учебное наблюдение;
- правила формирования оценки навыков;
- ограничения интерпретации результатов.

Способы передачи наблюдений в EducationSPD, интеграционные контракты, API,
хранение и математическая обработка будут зафиксированы отдельно.

### 2. Основной принцип

EducationSPD не устанавливает объективный факт наличия или отсутствия знания.
Сервис вычисляет предполагаемую степень освоения навыка по накопленной истории
завершённых учебных эпизодов.

Основой оценки является только результат, который стал итоговым для учебного
эпизода. Промежуточные действия студента сами по себе не являются наблюдениями.

Для SQL Module это означает:

- ввод и редактирование SQL не являются наблюдениями;
- предварительный запуск проверки не является наблюдением;
- отдельная отправленная попытка не является наблюдением;
- итог финализированного прохождения задания является наблюдением.

Таким образом, EducationSPD оценивает не процесс перебора решений, а результат,
которым закончилась самостоятельная работа студента над заданием.

### 3. Основные понятия

#### 3.1. Навык

**Навык** — именованная способность студента, предполагаемую степень освоения
которой система может оценивать по результатам учебной деятельности.

Примеры навыков SQL Module:

- получение корректного результирующего набора данных;
- использование `JOIN`;
- применение группировки;
- применение подзапросов;
- работа с несколькими таблицами;
- построение сложного SQL-запроса.

Навык должен иметь стабильный идентификатор, не зависящий от отображаемого
названия. Название и описание могут уточняться без потери накопленной истории.

Каждый учебный модуль владеет собственным каталогом навыков и отвечает за их
предметный смысл. EducationSPD не объединяет одноимённые навыки разных модулей
автоматически. Например, `sql:data-analysis` и `programming:data-analysis`
считаются разными навыками, потому что они проверяются в разных предметных
контекстах.

Навык однозначно определяется парой из стабильного ключа модуля и стабильного
ключа навыка. Например, модуль `sql` и навык `join` образуют идентификатор
`sql:join`.

Внутри модуля навыки делятся по происхождению:

- системные навыки вводятся разработчиками модуля при реализации его точных
  правил проверки;
- навыки-теги заявляются преподавателями при подготовке заданий и отражают их
  педагогическое содержание.

Происхождение навыка не ограничивает способы его дальнейшего использования.
Преподаватель может назначить существующий системный навык как тег задания, если
в этом задании навык не связан с отдельным весовым правилом. Создавать для этого
дублирующий пользовательский навык не требуется.

EducationSPD принимает определения модульных навыков и результаты наблюдений, но
не изменяет их смысл и не выступает источником их создания.

Одинаковые по смыслу навыки не должны создаваться повторно под разными названиями
внутри одного модуля. Порядок предотвращения и объединения таких дублей будет
определён при проектировании каталога навыков модуля.

Каталог навыков реализуется в каждом учебном модуле как самостоятельный CRUD.
Навык является отдельной сущностью и не хранится как вложенная изменяемая часть
задания. Системные навыки добавляются при разработке модуля, а преподаватели через
тот же каталог создают и используют пользовательские навыки-теги.

Существующий навык можно редактировать через CRUD. Его стабильный идентификатор
при этом сохраняется. Изменения названия, описания и остальных редактируемых
данных навыка применяются к каталогу модуля и к будущим публикациям заданий.

Редактирование навыка не создаёт новый навык и не обнуляет накопленную по нему
историю. Преподаватель отвечает за сохранение исходного педагогического смысла.
Если смысл меняется настолько, что старые и новые наблюдения больше нельзя
сопоставлять, преподаватель должен создать новый навык, заменить его в новой
версии задания, а прежний навык мягко удалить.

Перед сохранением изменений интерфейс должен явно предупреждать преподавателя,
что наблюдения до и после редактирования продолжат влиять на одну общую оценку
навыка и что существенное изменение смысла может исказить её.

Физическое удаление навыка, на который существуют ссылки, запрещается связями с
поведением `OnDelete Restrict`. Для пользовательского удаления применяется мягкое
удаление. Удалённый навык исключается из выбора для новых заданий, но сохраняется
для опубликованных снимков, завершённых эпизодов и исторических наблюдений.

#### 3.2. Весовое правило проверки

**Весовое правило проверки** — формализованное условие учебного задания, которое
модуль способен проверить однозначно. Правило имеет результат и вклад в итоговую
оценку задания.

Каждое весовое правило связывается с одним проверяемым навыком. Результат правила
является точным фактом выполнения или невыполнения соответствующего условия.

Например:

| Правило | Связанный навык |
|---|---|
| Получен правильный набор данных | Получение корректного результата |
| Использован обязательный `JOIN` | Использование `JOIN` |
| Применён обязательный `GROUP BY` | Применение группировки |
| Не использована запрещённая конструкция | Соблюдение ограничения задания |

Вес правила означает его вклад в балл задания. Вес не является вероятностью
достоверности проверки и не должен использоваться как её замена.

#### 3.3. Навык-тег

**Навык-тег** — способ привязки навыка к заданию целиком без отдельного весового
правила, которое непосредственно проверяет его проявление. Тегом может быть как
созданный преподавателем, так и существующий системный навык модуля.

Навыки-теги заявляются преподавателем и позволяют описывать более широкое
педагогическое содержание задания:

- работа с несколькими таблицами;
- анализ предметной области;
- построение сложных запросов;
- поиск способа решения;
- применение совокупности нескольких конструкций.

После создания навык-тег становится переиспользуемым навыком всего учебного
модуля. Он входит в общий каталог модуля и может назначаться другим заданиям, в
том числе другими преподавателями. Благодаря этому наблюдения по одному
педагогическому навыку накапливаются совместно независимо от конкретного задания.

При назначении тега преподаватель сначала выбирает существующий навык из каталога
модуля. Новый навык создаётся только тогда, когда подходящего навыка в каталоге
нет. Навык-тег не является локальной строковой меткой задания.

Один навык может оцениваться разными способами в разных заданиях. Например,
`sql:join` может быть связан с точным весовым правилом в одном задании и назначен
как косвенный тег в другом. Источник оценки сохраняется в наблюдении, поэтому
EducationSPD может различать точные и косвенные результаты одного навыка.

Навык-тег оценивается косвенно. Его положительное подтверждение возникает при
полном успешном выполнении задания. Такая оценка менее точна, чем результат
отдельного проверяемого правила, и это должно учитываться при последующей
математической обработке и отображении пользователю.

Все выводы, полученные через навыки-теги, являются явными допущениями модели, а
не результатами точной проверки. Перечень этих допущений должен быть доступен в
документации модели и учитываться в объяснениях пользователю.

#### 3.4. Попытка

**Попытка** — отдельная отправка решения на проверку внутри работы над заданием.

Попытка содержит важные диагностические данные, но не является самостоятельным
наблюдением EducationSPD. До завершения учебного эпизода студент может исправить
решение, изменить подход или отказаться от продолжения.

#### 3.5. Учебный эпизод

**Учебный эпизод** — непрерывная логическая работа студента над конкретным
заданием от начала прохождения до его финализации.

Учебный эпизод может включать любое количество попыток. Пока эпизод активен, его
результаты не изменяют оценку навыков в EducationSPD.

Один учебный эпизод формирует не более одного итогового наблюдения.

Покидание страницы выполнения задания завершает активный эпизод как неуспешный.
Закрытие вкладки, переход на другую страницу или возврат на платформу не
приостанавливают эпизод для последующего продолжения. Следующий вход в задание,
если повторное прохождение разрешено, создаёт новый учебный эпизод.

Это правило является явным допущением модели: уход со страницы трактуется как
решение прекратить выполнение задания и как отрицательный учебный результат.
Сервер не может мгновенно и безошибочно отличить закрытие страницы от потери сети
или аварийного завершения браузера. Поэтому присутствие определяется heartbeat
клиента с трёхминутным периодом ожидания переподключения.

Если студент возвращается в течение трёх минут после последнего heartbeat,
эпизод продолжается. Это позволяет безопасно обновить страницу или пережить
кратковременный разрыв соединения. Если присутствие не восстановлено за три
минуты, учебный модуль финализирует эпизод как неуспешный. Последующий вход
создаёт новый эпизод.

Явное действие «Вернуться на платформу» не ожидает истечения трёх минут и
немедленно финализирует эпизод как неуспешный.

Повторное прохождение того же задания после финализации предыдущего эпизода
создаёт новый учебный эпизод и новое самостоятельное наблюдение. Наблюдения не
перезаписывают и не заменяют друг друга, даже если относятся к одному студенту,
заданию и снимку задания.

#### 3.6. Снимок задания

**Снимок задания** — неизменяемое представление задания и всех условий его
выполнения, действовавших для конкретного учебного эпизода.

Снимок является единой единицей версии. Правила проверки, связи правил с
навыками, навыки-теги и остальные параметры задания не версионируются независимо
друг от друга. Они входят в один общий снимок задания.

Определения навыков хранятся отдельно в каталоге модуля. Общий снимок задания
фиксирует ссылки на навыки и способ их использования в задании: связь с весовым
правилом либо назначение в качестве тега. Вместе со ссылкой снимок сохраняет
актуальные на момент публикации данные навыка, необходимые для исторического
объяснения результата. Последующее редактирование навыка не изменяет уже
выпущенные снимки заданий.

Снимок включает как минимум:

- идентификатор исходного задания;
- содержимое и условия задания;
- конфигурацию проверки и проходной балл;
- весовые правила;
- связи весовых правил с навыками;
- набор навыков-тегов;
- ограничения числа попыток и учебного времени, если они применяются;
- идентификатор и дату создания снимка.

Учебный эпизод закрепляет один снимок задания. Все попытки и итоговое наблюдение
эпизода интерпретируются только по нему. Изменение задания преподавателем создаёт
новый снимок и не изменяет смысл уже начатых или завершённых эпизодов.

Новый снимок создаётся только при публикации задания. Промежуточные сохранения
черновика не создают снимков. После изменения опубликованного задания
преподаватель работает с новым черновиком, а его следующая публикация создаёт
новый неизменяемый снимок. Новые учебные эпизоды используют последний
опубликованный снимок, уже начатые продолжают использовать закреплённый ранее.

Изменение набора навыков задания, связей навыков с правилами или способа их
использования выполняется через новый черновик и вступает в силу только после
публикации нового снимка задания.

Наличие общего снимка не означает, что EducationSPD обязательно получает полное
содержимое задания. Состав данных, передаваемых сервису вместе с наблюдением,
будет определён отдельно при проектировании интеграции.

#### 3.7. Финализация

**Финализация** — переход учебного эпизода в окончательное состояние, после
которого студент больше не изменяет его результат.

Финализация происходит в одном из пяти случаев:

1. Студент получает 100 баллов. Эпизод завершается автоматически успешным
   результатом.
2. Студент получает меньше 100 баллов и явно принимает достигнутый результат как
   итоговый.
3. Студент явно прекращает выполнение задания и возвращается на платформу. Эпизод
   завершается неуспешным результатом.
4. Студент исчерпывает разрешённое количество попыток. Эпизод автоматически
   завершается неуспешным результатом, потому что студент не справился с заданием
   в установленных условиях.
5. Студент покидает страницу выполнения задания. Эпизод завершается неуспешным
   результатом и не может быть продолжен после повторного входа.

Истечение времени учитывается в зависимости от его предметного смысла:

- истечение учебного лимита времени на выполнение задания финализирует эпизод как
  неуспешный результат;
- техническое истечение сессии или её административное закрытие не считается
  наблюдением знаний.

Различие между учебным ограничением и техническим завершением определяет сам
учебный модуль. EducationSPD не выводит причину по времени или статусу сессии и
не переопределяет переданную модулем классификацию.

Техническое истечение серверной сессии, сбой инфраструктуры, ошибка песочницы или
административное закрытие не должны автоматически трактоваться как результат
знаний. При этом подтверждённая модулем потеря присутствия студента на странице
является отдельной причиной неуспешной финализации согласно принятому допущению.

#### 3.8. Итоговая попытка эпизода

Если студент получает 100 баллов, итоговой становится попытка, на которой был
достигнут этот результат, и эпизод завершается немедленно.

При финализации с результатом меньше 100 баллов итоговой становится лучшая
попытка учебного эпизода. Лучшей считается попытка с максимальным итоговым
баллом. При равном балле используется более ранняя попытка, первой достигшая
этого результата.

Наблюдение проверяемых навыков формируется целиком по одной итоговой попытке.
Результаты разных попыток нельзя объединять в искусственный набор успешно
выполненных правил, которого не было ни в одном фактическом решении студента.

Если студент явно отказался от задания, не выполнив ни одной попытки, точные
наблюдения навыков весовых правил отсутствуют. При этом сам учебный эпизод
завершается неуспешно, а навыки-теги оцениваются согласно явно принятым для них
допущениям.

#### 3.9. Учебное наблюдение

**Учебное наблюдение** — неизменяемый набор окончательных результатов навыков,
сформированный учебным модулем после финализации эпизода.

Наблюдение описывает факт, доступный системе в конкретный момент времени. Оно не
равно окончательному выводу о знании. Предполагаемая степень освоения вычисляется
позднее по совокупности наблюдений.

### 4. Формирование результатов навыков

#### 4.1. Навыки весовых правил

После финализации эпизода результат каждого выполненного весового правила
становится результатом связанного с ним навыка:

- правило выполнено — положительный результат навыка;
- правило не выполнено — отрицательный результат навыка.

Результат правила сохраняет смысл независимо от общего балла задания. Студент
может успешно выполнить одно условие и не выполнить другое. Это позволяет не
сводить оценку всех навыков к единому признаку «задание решено».

Пример итогового результата с оценкой 70 баллов:

| Весовое правило | Результат | Наблюдение навыка |
|---|---:|---|
| Правильный результирующий набор | Выполнено | Положительное |
| Обязательный `JOIN` | Выполнено | Положительное |
| Обязательный `GROUP BY` | Не выполнено | Отрицательное |

Правило и связанный навык должны соответствовать друг другу по смыслу. Если
правило проверяет только наличие определённой конструкции, навык не следует
описывать как более широкую способность, которую правило фактически не проверяет.

#### 4.2. Совместный результат конструкции и ответа

Наиболее точную характеристику освоения SQL-навыка даёт сочетание двух фактов:

1. студент выполнил правило применения требуемой конструкции;
2. студент получил правильный результат запроса.

Например, успешная проверка использования `JOIN` подтверждает выполнение
соответствующего формального условия. Одновременное получение правильного набора
данных дополнительно показывает, что конструкция применена в работоспособном
решении задачи.

EducationSPD должна сохранять оба результата как отдельные факты одного учебного
эпизода. Конкретный способ совместного учёта этих фактов будет определён в части,
посвящённой математической модели.

На этом уровне не утверждается, что запрос является оптимальным. Правильный
результат и выполнение формальных правил не доказывают оптимальность плана,
эффективность использования индексов, минимальную вычислительную сложность или
лучший из возможных способов решения. Оптимальность может считаться отдельным
навыком только при наличии самостоятельного точного правила её проверки.

#### 4.3. Явные допущения для навыков-тегов

Навыки-теги не имеют собственного точного правила. Поэтому они оцениваются по
общему результату задания на основании следующих явно принятых допущений:

- если задание выполнено на 100 баллов, считается, что студент проявил связанные
  с заданием навыки-теги;
- студент принял частичный результат — наблюдения по навыкам-тегам не
  формируются;
- если студент явно отказался от задания и вернулся на платформу, по всем
  связанным навыкам-тегам формируются отрицательные наблюдения;
- если студент покинул страницу выполнения задания, по всем связанным
  навыкам-тегам формируются отрицательные наблюдения;
- если студент исчерпал разрешённое количество попыток, по всем связанным
  навыкам-тегам формируются отрицательные наблюдения;
- если истёк учебный лимит времени, по всем связанным навыкам-тегам формируются
  отрицательные наблюдения;
- успешное выполнение задания не доказывает, что каждый навык-тег был необходим
  для выбранного студентом способа решения;
- корректность вывода зависит от того, насколько точно преподаватель подобрал
  навыки-теги к содержанию задания;
- положительный результат навыка-тега является косвенным свидетельством и не
  равен результату точного весового правила.

Частичный результат не должен преобразовываться в слабое отрицательное
наблюдение навыка-тега. Отсутствие положительного подтверждения не является
доказательством отсутствия навыка, поэтому такой тег не участвует в обновлении
его состояния по этому эпизоду.

Отрицательная оценка навыков-тегов при явном отказе, уходе со страницы,
исчерпании попыток или учебного лимита времени также является допущением. Она
отражает неуспешное завершение учебного эпизода, но не доказывает точное
отсутствие каждого связанного с заданием навыка.

### 5. Соотношение результата задания и навыков

Общий результат задания и результаты отдельных навыков являются разными уровнями
оценки.

Возможны следующие ситуации:

- задание выполнено полностью, все обязательные правила выполнены, навыки-теги
  подтверждены;
- задание выполнено частично, часть проверяемых навыков получила положительный
  результат, часть — отрицательный, наблюдения по навыкам-тегам не формируются;
- студент прекратил выполнение, итог эпизода отрицательный, но результаты
  выполненных проверок могут быть сохранены как часть наблюдения;
- учебный эпизод завершился по технической причине и не создаёт обычного
  наблюдения знаний.

СППР не должна автоматически приравнивать частичное или неуспешное выполнение
задания к провалу каждого связанного с ним проверяемого навыка. Источником точного
результата проверяемого навыка является соответствующее правило.

### 6. Накопление знаний

Результат одного эпизода недостаточен для окончательного вывода об освоении
навыка. Один правильный ответ может быть случайным, а одна ошибка может быть
следствием невнимательности или неверного понимания конкретного задания.

Текущее состояние навыка является общим для студента в пределах учебного модуля
и однозначно определяется сочетанием студента, модуля и навыка. Переход между
курсами, группами, практиками или открытым банком заданий не создаёт новую
независимую оценку и не обнуляет накопленную историю.

Наблюдение не содержит идентификаторы курса, группы и практики. Преподавательская
аналитика получает актуальный состав группы из Education и сопоставляет его с
общими состояниями навыков студентов. Контекст платформенной организации
обучения не дублируется в потоке наблюдений учебных модулей.

Все финализированные эпизоды сохраняются в истории. Степень влияния повторных
прохождений одного задания на итоговую оценку будет определена математической
моделью и не меняет сам факт наличия отдельных наблюдений.

EducationSPD формирует оценку по истории наблюдений:

```text
Финализированные учебные эпизоды
        ↓
Результаты проверяемых навыков и навыков-тегов
        ↓
Накопленная история наблюдений
        ↓
Предполагаемая степень освоения навыка
        ↓
Рекомендации студенту и преподавателю
```

Первичные наблюдения должны сохраняться отдельно от рассчитанного текущего
состояния навыка. Это позволит:

- объяснять происхождение оценки;
- изменять математическую модель;
- пересчитывать состояние знаний;
- сравнивать версии алгоритма;
- исправлять ошибочные или отменённые результаты без потери истории.

### 7. Ограничения интерпретации

Оценка EducationSPD является вероятностной педагогической оценкой, а не
сертификацией знания и не доказательством профессиональной компетентности.

При интерпретации необходимо учитывать:

- проверяется только то, для чего модуль имеет формализованное правило;
- навык правила не должен иметь более широкий смысл, чем сама проверка;
- правильность результата не означает оптимальность решения;
- навык-тег оценивается косвенно на основании явно описанных допущений;
- небольшое количество наблюдений даёт менее устойчивую оценку;
- результат зависит от качества заданий и корректности связей между правилами,
  тегами и навыками;
- преподаватель отвечает за педагогическую корректность назначенных заданию
  навыков-тегов и их соответствие содержанию задания;
- преподаватель отвечает за сохранение педагогического смысла навыка при его
  редактировании; система предупреждает о влиянии изменений на накопленную
  историю, но не может проверить смысловую эквивалентность автоматически.

Пользовательские интерфейсы должны использовать формулировки «предполагаемый
уровень освоения», «оценка модели» и «рекомендация». Формулировки вида «студент
точно знает» или «студент не знает» недопустимы.

### 8. Инварианты первой части концепции

1. EducationSPD не зависит от предметной области SQL Module.
2. SQL Module является первым, но не единственным возможным источником
   наблюдений.
3. Каждый учебный модуль владеет собственным каталогом навыков.
4. Системные навыки вводятся разработчиками модуля, навыки-теги заявляются
   преподавателями.
5. Созданный навык-тег становится переиспользуемым навыком всего модуля, а не
   локальной меткой одного задания.
6. Системный навык можно назначить как тег задания; источник оценки определяется
   привязкой в конкретном задании.
7. Навыки хранятся отдельным CRUD в учебном модуле, удаляются мягко, а физические
   связи защищаются `OnDelete Restrict`.
8. Навык можно редактировать без изменения его стабильного идентификатора;
   изменения применяются только к будущим снимкам заданий.
9. Редактирование навыка не обнуляет историю; ответственность за сохранение его
   смысла несёт преподаватель, которому выводится явное предупреждение.
10. EducationSPD не изменяет предметный смысл навыков учебного модуля.
11. Наблюдение создаётся только для финализированного учебного эпизода.
12. Промежуточная попытка не является наблюдением EducationSPD.
13. Один учебный эпизод формирует не более одного итогового наблюдения.
14. Каждое повторное прохождение после финализации создаёт новый эпизод и новое
    наблюдение; предыдущие наблюдения не перезаписываются.
15. Покидание страницы финализирует текущий эпизод как неуспешный; повторный вход
    создаёт новый эпизод.
16. Отсутствие heartbeat допускает переподключение в течение трёх минут; после
    этого модуль финализирует эпизод, а явный возврат завершает его немедленно.
17. Учебный эпизод закрепляет один неизменяемый общий снимок задания.
18. Правила, связи с навыками и навыки-теги входят в общий снимок и не
    версионируются независимо друг от друга.
19. Изменение навыков и их связей в задании требует публикации нового снимка.
20. Новый снимок задания создаётся при публикации; сохранение черновика снимок не
    создаёт.
21. При достижении 100 баллов итоговой становится текущая попытка; в остальных
    случаях используется лучшая попытка эпизода.
22. Наблюдение правил формируется по одной фактической попытке и не собирается из
    лучших результатов разных попыток.
23. Каждое весовое правило связано с одним проверяемым навыком.
24. Результат весового правила является точным результатом связанного навыка.
25. Вес правила означает вклад в оценку задания, а не достоверность проверки.
26. Наиболее точная характеристика SQL-навыка образуется при совместном успешном
   результате правила конструкции и правила правильного ответа.
27. В первой версии принимается явное допущение: полное успешное выполнение
    задания даёт положительное косвенное наблюдение его навыков-тегов.
28. В первой версии принимается явное допущение: явный отказ от задания даёт
    отрицательные косвенные наблюдения его навыков-тегов.
29. Покидание страницы финализирует эпизод как неуспешный и даёт отрицательные
    косвенные наблюдения его навыков-тегов.
30. Исчерпание попыток финализирует эпизод как неуспешный и даёт отрицательные
    косвенные наблюдения его навыков-тегов.
31. Частичный принятый результат не формирует наблюдений по навыкам-тегам.
32. Истечение учебного лимита времени считается неуспешным наблюдением, а
    техническое или административное завершение сессии — не считается.
33. Учебный модуль определяет смысл причины завершения, EducationSPD её не
    переопределяет.
34. Техническая ошибка не должна превращаться в отрицательное наблюдение знания.
35. Первичные наблюдения отделяются от вычисляемого состояния навыка.
36. Состояние навыка общее для сочетания студента, модуля и навыка; курс и группа
    сохраняются как контекст наблюдения, но не создают отдельную оценку.
37. Оценка навыка является вероятностной и должна сопровождаться объяснением её
    ограничений.

### 9. За пределами первой части

Отдельного обсуждения и последующей фиксации требуют:

- получение EducationSPD определений навыков из каталогов учебных модулей;
- структура интеграционного события;
- идемпотентность и исправление наблюдений;
- связь пользователей, учебных групп и модулей;
- математическая модель накопления знаний;
- использование BKT и настройка её параметров;
- ранжирование заданий и применение метода анализа иерархий;
- формирование объяснений рекомендаций;
- API студента, преподавателя и разработчика модели.

## Часть 2. Получение наблюдений EducationSPD

### 10. Асинхронная доставка

Учебные модули передают финализированные наблюдения в EducationSPD асинхронно
через Kafka. Завершение учебного эпизода не зависит от доступности EducationSPD и
не ожидает применения наблюдения к модели знаний.

Учебный модуль должен атомарно зафиксировать финализацию эпизода и подготовить
сообщение к публикации. Для этого используется transactional outbox модуля.
Фоновый издатель доставляет сохранённое сообщение в Kafka и повторяет отправку
при временной ошибке.

EducationSPD является потребителем событий наблюдений. Обработка должна быть
идемпотентной: повторная доставка одного события не создаёт повторного
наблюдения и не изменяет состояние навыков второй раз.

Из асинхронной модели следуют ограничения согласованности:

- учебный модуль может уже показать студенту итог, пока EducationSPD ещё не
  обработала событие;
- рекомендации и аналитика обновляются с небольшой задержкой;
- временная недоступность EducationSPD или Kafka не отменяет результат эпизода;
- после восстановления доставки накопленные события должны быть обработаны без
  потери и дублирования наблюдений.

Конкретное имя топика, структура события и политика повторной обработки будут
определены следующими решениями.

### 11. Гранулярность события

Один финализированный учебный эпизод публикуется одним интеграционным событием.
Событие содержит коллекцию всех сформированных результатов навыков.

Логическая структура события:

```text
LearningEpisodeFinalized
├── EventId
├── EpisodeId
├── StudentId
├── ModuleKey
├── TaskId
├── FinalizedAt
└── SkillResults[]
```

`FinalScore` в событие не включается. Учебный модуль уже преобразовал итог
задания в окончательные результаты навыков, а EducationSPD не дублирует
модульную аналитику по баллам. Поле может быть добавлено новой версией контракта,
если появится подтверждённый сценарий его использования.

Причина финализации также не передаётся. Она принадлежит учебному модулю и уже
учтена им при формировании окончательных результатов навыков.

Минимальный результат навыка содержит:

```text
SkillId
Source = ValidationRule | TaskTag
Outcome = Succeeded | Failed
```

Вес правила, текст правила, баллы и технические детали проверки не передаются.

Один `SkillId` может присутствовать в событии эпизода не более одного раза. В
закреплённом снимке задания навык используется либо через одно точное весовое
правило, либо как навык-тег. Одновременная привязка одного навыка обоими
способами и привязка одного навыка к нескольким правилам одного задания
запрещаются валидацией при публикации.

EducationSPD не выбирает приоритет между конфликтующими результатами одного
навыка. Событие, нарушающее уникальность `SkillId`, считается некорректным и не
применяется к модели знаний.

Результат навыка содержит стабильный идентификатор навыка, источник оценки,
результат и связанные с оценкой параметры. Название, описание и другие данные
определения навыка в событии эпизода не дублируются.

Событие не переносит полный снимок задания и не содержит его идентификатор.
Учебный модуль уже сформировал окончательные результаты навыков по закреплённому
снимку, а EducationSPD не должна повторно интерпретировать правила задания.
Источником и владельцем снимка остаётся учебный модуль.

EducationSPD должен получать актуальные определения навыков отдельным
механизмом. Объяснения и пользовательские представления используют сведения из
локальной проекции каталога, а не копии определения в каждом наблюдении.

EducationSPD обрабатывает событие атомарно: сохраняет эпизод и все входящие в
него наблюдения навыков в одной транзакции. Частичное сохранение события, при
котором применена только часть результатов навыков, недопустимо.

Отдельные события на каждый навык не публикуются. Это сохраняет связь результатов
правил с общим результатом задания, упрощает идемпотентность и исключает
появление частично обработанных учебных эпизодов.

### 12. Синхронизация каталога навыков

Каталог навыков каждого учебного модуля синхронизируется с EducationSPD
асинхронно через Kafka. Учебный модуль остаётся источником истины, EducationSPD
хранит локальную проекцию каталога для обработки наблюдений, аналитики и
пользовательских представлений.

События каталога и события финализированных эпизодов публикуются в разные
Kafka-топики:

```text
learning.skill-catalog
learning.episode-finalized
```

Точные имена могут быть уточнены при реализации, но логическое разделение
топиков является обязательным. Для них используются отдельные контракты,
потребители, политики повторной обработки и мониторинг отставания.

Топик `learning.skill-catalog` использует log compaction. Для каждого ключа
`ModuleKey + SkillId` Kafka сохраняет последнее опубликованное состояние навыка.
Это позволяет новому экземпляру EducationSPD восстановить локальную проекцию
каталога без отдельного HTTP-запроса полной синхронизации.

Мягкое удаление навыка публикуется как новое состояние с `IsDeleted = true`.
Kafka tombstone для него не используется, потому что определение удалённого
навыка должно оставаться доступным для исторических наблюдений.

Модуль публикует события следующих видов:

- создание навыка;
- изменение навыка;
- мягкое удаление навыка.

События каталога содержат определение навыка. Эти данные публикуются при
изменении каталога и не дублируются в каждом событии учебного эпизода.

Публикация событий каталога также выполняется через transactional outbox
учебного модуля. EducationSPD применяет их идемпотентно. Мягко удалённый навык
остаётся в локальной проекции и исторических наблюдениях, но помечается
недоступным для нового использования.

Если событие эпизода ссылается на навык, определение которого ещё не поступило,
EducationSPD не отбрасывает наблюдение. Оно сохраняется для последующей обработки
после синхронизации каталога.

Порядок между разными топиками не гарантируется. Поэтому корректность обработки
эпизода не должна зависеть от того, какое из событий физически поступило первым.

### 13. Ключи партиционирования

События каталога навыков публикуются с ключом, составленным из ключа модуля и
идентификатора навыка:

```text
ModuleKey + SkillId
```

Это сохраняет порядок создания, последовательных изменений и мягкого удаления
конкретного навыка, не ограничивая параллельную обработку разных навыков.

События финализированных эпизодов публикуются с ключом, составленным из ключа
модуля и идентификатора студента:

```text
ModuleKey + StudentId
```

Все наблюдения одного студента внутри одного учебного модуля попадают в одну
партицию и обрабатываются последовательно. Наблюдения разных студентов могут
обрабатываться параллельно.

### 14. Идемпотентность событий эпизодов

Обработка событий финализированных эпизодов защищается на двух уровнях.

`EventId` идентифицирует конкретное интеграционное событие. Повторная доставка
события с тем же `EventId` не создаёт новых записей и не применяет результаты
навыков повторно.

Сочетание `ModuleKey + EpisodeId` является бизнес-идентификатором учебного
эпизода и должно быть уникальным в EducationSPD. Если поступает событие с новым
`EventId`, но уже принятым сочетанием `ModuleKey + EpisodeId`, оно не
перезаписывает существующее наблюдение и рассматривается как конфликт данных,
требующий диагностики.

Таким образом, обычные повторы доставки обрабатываются без ошибки, а появление
двух различных итогов одного эпизода не скрывается молчаливым обновлением.

### 15. Неизменяемость принятого наблюдения

В первой версии принятое наблюдение эпизода является окончательным и
неисправимым. EducationSPD не поддерживает изменение, отмену или замену уже
принятого результата.

Событие с новым `EventId` для существующего сочетания `ModuleKey + EpisodeId` не
считается исправлением и остаётся конфликтом данных. Ошибочно сформированное
наблюдение сохраняет исходное влияние на модель знаний.

Компенсирующие события и пересчёт после административной отмены могут быть
добавлены в будущих версиях контракта, но не входят в первую реализацию.

### 16. Время наблюдения

Предметным временем наблюдения является `FinalizedAt` — момент финализации
учебного эпизода, установленный учебным модулем.

Задержка публикации, время нахождения события в Kafka и момент его обработки
EducationSPD не изменяют положение наблюдения в учебной истории. Технические
метки доставки могут использоваться инфраструктурой для логирования и
мониторинга, но не входят в педагогический смысл наблюдения и не применяются
математической моделью.

### 17. Идентификация студента

Студент идентифицируется в событии только глобальным `UserId`, совпадающим со
значением Identity `sub`. Учебные модули не передают в событии эпизода ФИО,
email, роль и другие персональные атрибуты пользователя.

EducationSPD связывает наблюдения одного студента по стабильному глобальному
идентификатору. Отображаемые данные пользователя и состав учебных групп при
необходимости получаются из Education отдельным контрактом и не дублируются в
потоке учебных наблюдений.

Идентификаторы курса, группы и практики также не передаются. Наблюдение содержит
только контекст учебного модуля и задания, необходимый для общей оценки навыков
внутри модуля.

### 18. Надёжный приём через inbox

Kafka-consumer не применяет событие эпизода непосредственно к модели знаний.
Сначала он сохраняет событие в durable inbox EducationSPD и только после
успешной фиксации подтверждает Kafka offset.

Inbox использует состояния:

- `Received` — событие сохранено и ожидает обработки;
- `PendingCatalog` — событие ссылается на навык, которого ещё нет в локальной
  проекции каталога;
- `Applied` — эпизод и его результаты навыков успешно применены;
- `Failed` — событие окончательно признано некорректным и требует диагностики.

Повторная доставка не создаёт новую inbox-запись благодаря уникальному
`EventId`. Сохранение события и применение его к модели выполняются раздельно,
поэтому перезапуск EducationSPD после подтверждения Kafka offset не приводит к
потере наблюдения.

События применяются последовательно для сочетания `ModuleKey + StudentId`.
Если ранний эпизод ожидает неизвестный навык, последующие эпизоды того же
студента в том же модуле также ожидают. При этом обработка других студентов не
блокируется, даже если их Kafka-сообщения находились в той же партиции.

После поступления определения навыка обработчик сначала применяет ожидающий
ранний эпизод, затем продолжает последующие события студента в порядке их
`FinalizedAt`.

Событие может поступить позже уже обработанных эпизодов, хотя его `FinalizedAt`
раньше. В таком случае EducationSPD вставляет наблюдение в правильное место
хронологической истории и пересчитывает только затронутые навыки этого студента.
При одинаковом `FinalizedAt` используется детерминированный порядок по
`EpisodeId`.

Порядок доставки Kafka не используется как педагогический порядок наблюдений.
Это необходимо для BKT, поскольку последовательности «успех, затем провал» и
«провал, затем успех» дают разное состояние освоения из-за перехода обучения
между эпизодами.

## Часть 3. Математическая модель знаний

### 19. Базовая модель BKT

Для вычисления предполагаемой степени освоения навыка используется Bayesian
Knowledge Tracing. Для каждого сочетания `StudentId + ModuleKey + SkillId`
модель хранит вероятность нахождения навыка в освоенном состоянии.

Базовые параметры модели:

- `P(L0)` — начальная вероятность освоения;
- `P(T)` — вероятность перехода в освоенное состояние после учебной возможности;
- `P(G)` — вероятность успешного результата без освоенного навыка;
- `P(S)` — вероятность неуспешного результата при освоенном навыке.

Источник наблюдения влияет на параметры интерпретации результата:

- для `ValidationRule` используются низкие `P(G)` и `P(S)`, потому что результат
  получен точным правилом модуля;
- для `TaskTag` используются более высокие `P(G)` и `P(S)`, потому что результат
  основан на явно принятых косвенных допущениях.

Источник не преобразуется в фиксированный числовой вес. Его влияние определяется
параметрами выбранной математической модели.

В первой реализации допускаются общие `P(L0)` и `P(T)` и два набора `P(G)` и
`P(S)` для точных правил и тегов. Конкретные значения, формулы обновления,
калибровка, влияние повторного прохождения задания и применение перехода обучения
после разных результатов будут определены отдельным обсуждением.

Исходные наблюдения сохраняются независимо от вычисленного состояния навыка,
чтобы модель можно было пересчитать после изменения параметров.

### 20. Разделение BKT и ранжирования

BKT отвечает только за оценку предполагаемой степени освоения навыка. Метод
анализа иерархий и другие механизмы ранжирования не изменяют состояние знаний и
будут использовать результаты BKT позднее при выборе рекомендуемых заданий.

## Часть 4. Формирование рекомендаций

### 21. Граница отбора кандидатов

Учебный модуль самостоятельно формирует список заданий, которые разрешено
рекомендовать конкретному студенту. Только модуль знает актуальное состояние
заданий, правила публикации, ограничения доступа и состояние прохождения.

EducationSPD не хранит копию каталога заданий, не определяет доступность задания
и не пытается обнаружить закрытые задания. Сервис получает уже отфильтрованный
набор кандидатов, ранжирует его и возвращает идентификаторы заданий вместе с
объяснением порядка.

Ответственность разделяется следующим образом:

```text
Учебный модуль → отбор допустимых кандидатов
EducationSPD   → ранжирование и объяснение
Учебный модуль → student-safe ответ пользователю
```

Учебный модуль обязан повторно проверить доступность выбранного задания перед
его открытием, потому что состояние каталога может измениться после получения
рекомендации.

### 22. Синхронное ранжирование

Учебный модуль запрашивает ранжирование кандидатов синхронным HTTP-вызовом
EducationSPD. Рекомендация формируется в рамках пользовательского запроса и
возвращается модулю непосредственно в ответе.

Асинхронная Kafka-интеграция используется для накопления наблюдений и
синхронизации каталога навыков. Для запроса ранжирования Kafka не используется,
поскольку запрос и ответ должны быть связаны с текущим действием пользователя.

Логическая последовательность:

```text
Студент запрашивает рекомендации
        ↓
Модуль формирует допустимых кандидатов
        ↓
Модуль вызывает EducationSPD по HTTP
        ↓
EducationSPD возвращает упорядоченный результат
        ↓
Модуль формирует student-safe ответ
```

Вызов выполняется между доверенными сервисами. Способ сервисной аутентификации,
таймауты и fallback-поведение будут определены отдельно при проектировании API.

### 23. Общая шкала сложности

Кандидат на рекомендацию содержит нормализованный уровень сложности от 1 до 5:

| Значение | Интерпретация |
|---:|---|
| 1 | Начальное |
| 2 | Простое |
| 3 | Среднее |
| 4 | Сложное |
| 5 | Продвинутое |

Каждый учебный модуль сам назначает уровень или преобразует собственную шкалу в
этот диапазон. EducationSPD не интерпретирует предметную сложность задания и не
вычисляет её по содержимому.

Общая шкала используется только внутри ранжирования кандидатов, уже отобранных
одним учебным модулем. Она не означает, что задания разных предметных модулей
можно напрямую сравнивать между собой.

### 24. Минимальный состав кандидата

Каждый кандидат персонализированного ранжирования должен содержать минимум один
навык. Задание без навыков не может быть связано с дефицитами студента и не
передаётся в EducationSPD для персонализированной рекомендации.

Минимальный кандидат содержит:

```text
TaskId
DifficultyLevel
Skills[]
  ├── SkillId
  └── Source = ValidationRule | TaskTag
```

Модуль может хранить и показывать задания без разметки навыков самостоятельно.
Если после проверки доступа не осталось размеченных кандидатов, модуль применяет
собственный неперсонализированный fallback и не обращается к EducationSPD.

### 25. Критерии ранжирования

EducationSPD ранжирует кандидатов по четырём критериям, которые вычисляются из
состояний навыков, истории эпизодов и переданного описания кандидата:

1. **Дефицит навыков** — насколько слабо освоены навыки задания.
2. **Соответствие сложности** — насколько сложность задания соответствует
   текущему состоянию связанных навыков.
3. **Новизна задания** — насколько часто студент уже проходил это задание.
4. **Диагностическая ценность** — какая доля навыков задания оценивается точными
   правилами, а не косвенными тегами.

Критерии нормализуются в диапазон от 0 до 1. Большее значение всегда означает
большую предпочтительность кандидата.

#### 25.1. Дефицит навыков

Для каждого навыка вычисляется дефицит:

```text
SkillDeficit = 1 - MasteryProbability
```

Критерий задания равен среднему дефициту его навыков. Если по навыку ещё нет
наблюдений, используется начальная вероятность `P(L0)` текущей модели BKT.

#### 25.2. Соответствие сложности

Целевой уровень сложности определяется по среднему предполагаемому освоению
навыков кандидата:

| Средняя вероятность освоения | Целевая сложность |
|---:|---:|
| менее 0.30 | 1 |
| 0.30–0.49 | 2 |
| 0.50–0.69 | 3 |
| 0.70–0.84 | 4 |
| 0.85 и выше | 5 |

Оценка соответствия:

```text
DifficultyFit = 1 - Abs(CandidateDifficulty - TargetDifficulty) / 4
```

#### 25.3. Новизна задания

Новизна снижает постоянную рекомендацию одного и того же задания:

```text
Novelty = 1 / (1 + FinalizedEpisodeCountForTask)
```

Первое прохождение получает значение 1, последующие постепенно уменьшают вклад
критерия. Низкая новизна не запрещает повторную рекомендацию, если задание хорошо
закрывает выраженный дефицит навыков.

#### 25.4. Диагностическая ценность

Критерий показывает, насколько точно следующий результат сможет уточнить модель:

```text
DiagnosticValue = ValidationRuleSkillCount / AllCandidateSkillCount
```

Задание, где все навыки связаны с точными правилами, получает 1. Задание только с
навыками-тегами получает 0. Этот критерий имеет наименьший приоритет и не должен
вытеснять педагогически полезное задание с тегами.

### 26. Метод анализа иерархий

МАИ используется для получения весов критериев, а не для изменения состояний
навыков. Базовая матрица попарных сравнений:

| Критерий | Дефицит | Сложность | Новизна | Диагностичность |
|---|---:|---:|---:|---:|
| Дефицит | 1 | 3 | 5 | 7 |
| Сложность | 1/3 | 1 | 3 | 4 |
| Новизна | 1/5 | 1/3 | 1 | 2 |
| Диагностичность | 1/7 | 1/4 | 1/2 | 1 |

Она задаёт приблизительные приоритеты:

```text
Дефицит навыков         ≈ 0.57
Соответствие сложности ≈ 0.25
Новизна                 ≈ 0.11
Диагностическая ценность ≈ 0.07
```

Матрица и рассчитанные веса являются конфигурацией модели. При изменении матрицы
EducationSPD проверяет положительность значений, взаимную обратность элементов и
отношение согласованности. Матрица с `CR > 0.10` не может быть активирована.

Итоговый рейтинг кандидата:

```text
RankScore =
    KnowledgeDeficitWeight * KnowledgeDeficit +
    DifficultyFitWeight * DifficultyFit +
    NoveltyWeight * Novelty +
    DiagnosticValueWeight * DiagnosticValue
```

Кандидаты сортируются по убыванию `RankScore`, при равенстве — по `TaskId`. Это
делает результат детерминированным.

### 27. Холодный старт

Если у студента ещё нет наблюдений по навыку, используется `P(L0)`. Поэтому
EducationSPD может ранжировать задания до появления персональной истории.

При полностью новой модели преимущество получают задания, которые:

- соответствуют начальному уровню сложности;
- ещё не проходились студентом;
- содержат навыки с точными правилами.

Холодный старт не требует отдельного случайного алгоритма.

### 28. Ответ ранжирования и объяснение

EducationSPD возвращает только результаты для переданных кандидатов:

```text
TaskId
Rank
RankScore
Reasons[]
  ├── Code
  ├── Contribution
  └── SkillIds[]
```

Причины являются структурированными и не содержат предметный текст задания.
Базовые коды:

- `TargetsWeakSkills`;
- `DifficultyMatchesCurrentLevel`;
- `TaskIsNewForStudent`;
- `ProvidesPreciseAssessment`.

`Contribution` показывает вклад критерия в итоговый рейтинг. Учебный модуль
использует структурированное объяснение и собственные данные задания для
формирования student-safe ответа и локализованного пользовательского текста.

EducationSPD не возвращает задания, которых не было во входном списке, и не
изменяет переданные идентификаторы.

### 29. Отказоустойчивость рекомендации

Синхронное ранжирование не должно становиться обязательным условием открытия
учебного модуля. Модуль задаёт короткий тайм-аут вызова EducationSPD и при
недоступности сервиса применяет собственный неперсонализированный fallback.

EducationSPD не резервирует задание и не гарантирует, что оно останется
доступным после ранжирования. Перед открытием задания модуль повторно проверяет
его публикацию, доступность и ограничения студента.

Запрос ранжирования является идемпотентным и не изменяет модель знаний. Повторный
запрос с одинаковым состоянием модели, конфигурацией и списком кандидатов должен
дать тот же порядок. Результат можно кратковременно кэшировать по студенту,
модулю и отпечатку кандидатов. Получение нового наблюдения студента инвалидирует
его кэш рекомендаций в соответствующем модуле.

### 30. Хранение и пересчёт состояния знаний

EducationSPD хранит раздельно:

- неизменяемые принятые наблюдения;
- актуальное вычисленное состояние каждого навыка студента;
- версию математической модели и её параметры;
- техническое состояние обработки события.

Проекция состояния навыка является производной и может быть полностью
восстановлена из наблюдений. Она не является первичным источником истины.

Каждое применённое наблюдение фиксирует версию модели, которой оно было
обработано. При активации новой версии параметров выполняется фоновый пересчёт
проекций из исходных наблюдений. До завершения пересчёта сервис продолжает
обслуживать чтение из последней целостной версии проекций; частично пересчитанное
состояние пользователям не публикуется.

Позднее событие вставляется в хронологическую последовательность по
`FinalizedAt`, затем `EpisodeId`, после чего пересчитываются затронутые навыки
этого студента начиная с точки вставки. Пересчёт одного студента не блокирует
обработку других студентов.

### 31. Граница первой версии

В первую версию входят:

- синхронизация каталога навыков модулей;
- приём финализированных учебных эпизодов через Kafka;
- идемпотентное хранение наблюдений;
- расчёт вероятности освоения навыков по BKT;
- получение состояния навыков студента;
- синхронное ранжирование переданных кандидатов;
- структурированное объяснение результата;
- восстановление проекций из журнала наблюдений.

В первую версию не входят автоматическая калибровка параметров, исправление уже
принятых наблюдений, межмодульное сопоставление навыков, сравнение студентов,
прогноз итоговой оценки курса и генерация заданий. Эти возможности требуют
отдельного проектного решения и не должны скрыто появляться в MVP.
