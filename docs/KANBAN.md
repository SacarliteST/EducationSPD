# Kanban: EducationSPD MVP

Источники требований:

- [CONCEPT.md](CONCEPT.md) — предметные решения и допущения;
- [TZ.md](TZ.md) — технические контракты и критерии приёмки.

Доска покрывает разработку EducationSPD и отдельный интеграционный контур SQL
Module. Изменения в SQL Module выполняются только после готовности соответствующих
контрактов EducationSPD и в его собственном репозитории.

## Правила доски

Статусы:

```text
Backlog → Ready → In progress → Review → Done
                         └──────→ Blocked
```

`Blocked` используется только при наличии конкретного внешнего блокера. Задача
переводится в `Done`, когда выполнены её критерии, добавлены необходимые тесты и
создан отдельный task-scoped commit. Push и deploy в Definition of Done не входят.

При реализации применяются локальные repository skills. Миграции и OpenAPI
генерируются только вне sandbox. Новые HTTP endpoint реализуются только через
ASP.NET Core Controllers.

### SPD-003 — Типизированная конфигурация и service authentication

Добавить options для PostgreSQL, Kafka, inbox, модели и service authentication.
Подключить `ValidateOnStart`. Реализовать проверку `X-Service-Key` для прикладных
controller endpoints; health endpoints оставить без ключа.

Готово, когда:

- отсутствующая или некорректная обязательная конфигурация останавливает host;
- секрет не имеет рабочего значения по умолчанию и не логируется;
- отсутствие ключа даёт `401`, неверный ключ — `403`;
- корректный ключ пропускает запрос;
- проверка ключа не использует обычное строковое сравнение.

**Выполнено 2026-11-07.** Добавлены валидируемые при старте options PostgreSQL,
Kafka, inbox, математической модели и service authentication. Прикладные
Controllers защищены `X-Service-Key`, отсутствующий ключ возвращает `401`,
неверный — `403`; сравнение выполняется по SHA-256 через
`CryptographicOperations.FixedTimeEquals`. Health остаётся анонимным. Секрет не
имеет значения по умолчанию и задаётся тестами/окружением.

Готово, когда:

- изменение имени сохраняет идентичность навыка;
- soft-delete сохраняет историческую запись;

**Выполнено 2026-11-07.** Добавлена доменная

Уникальность `(ModuleKey, SkillId)`, длины и допустимые значения origin
закреплены миграцией и PostgreSQL integration tests.

### SPD-006 — Универсальный durable inbox

Реализовать хранение raw payload, hash, типа, версии, статуса, ошибки и retry
metadata. Inbox должен отделять сохранение транспорта от предметного применения.

Готово, когда:

- повторный `EventId` с тем же payload идемпотентен;
- повторный `EventId` с другим payload фиксируется как конфликт;
- переходы `Received/PendingCatalog/Applied/Failed` валидируются;
- сообщение сохраняется до Kafka offset commit;
- операции пригодны для пакетного фонового чтения без гонок.

**Выполнено 2026-11-07.** Добавлены доменная
модель inbox, хранение raw JSON в `jsonb`, SHA-256, тип и версия сообщения,
статусы, безопасный код ошибки и retry metadata. Вставка через
`ON CONFLICT DO NOTHING` различает повтор и конфликт payload. Пакетный executor
обрабатывает готовые строки в транзакции с `FOR UPDATE SKIP LOCKED`, поэтому
параллельные обработчики получают разные сообщения. Переходы состояний и
операционный restart закреплены доменными и PostgreSQL integration tests.

### SPD-007 — Consumer каталога навыков

Подключить Kafka consumer `learning.skill-catalog`, сохранение inbox и применение
актуального состояния навыка.

Готово, когда:

- сообщение сначала фиксируется в PostgreSQL;
- offset подтверждается только после сохранения;
- дубликат не применяет изменение второй раз;
- старое событие не откатывает новое;
- soft-delete применяется как состояние, не Kafka tombstone;
- неизвестная версия становится неисправимой безопасной ошибкой;
- тест проходит на реальном Kafka broker и PostgreSQL Testcontainers.

**Выполнено 2026-11-07.** Добавлены Kafka consumer с ручным подтверждением
offset после durable-записи, отдельный транзакционный обработчик inbox и
application-сценарий обновления каталога. Обработка разделена по типам сообщений,
дубликат не применяется повторно, старое событие не откатывает проекцию, а удаление
остаётся soft-delete. Неизвестная версия получает безопасный окончательный код
`UnsupportedSchemaVersion`. Сквозной integration test использует реальные Kafka и
PostgreSQL Testcontainers и проверяет состояние inbox до запуска предметного
обработчика.

### SPD-009 — Consumer финализированных эпизодов

Реализовать валидацию, идемпотентное применение эпизода и сохранение всех его
наблюдений одной транзакцией.

Готово, когда:

- корректный эпизод сохраняется целиком;
- повторная доставка не создаёт данных;
- другой `EventId` для существующего эпизода даёт `EpisodeConflict`;
- частично сохранённый эпизод невозможен;
- неизвестный навык не теряет сообщение;
- raw payload не попадает в Information-логи.

**Выполнено 2026-11-07.** Общий durable Kafka consumer переиспользован для
`learning.episode-finalized`: offset подтверждается только после записи raw JSON в
inbox. Проверенный эпизод и все его наблюдения сохраняются в транзакции обработки
inbox; повторная доставка идемпотентна, а другой `EventId` для существующей пары
`ModuleKey + EpisodeId` получает безопасный `EpisodeConflict`. Событие с
неизвестным навыком остаётся в `PendingCatalog` без частично сохранённого эпизода.
Логи содержат только тип сообщения и идентификаторы, но не raw payload. Сквозной
тест на реальных Kafka и PostgreSQL проверяет успешное применение, дубликат,
конфликт и отсутствующий каталог.

### SPD-010 — PendingCatalog и независимая очередь студентов

Реализовать ожидание отсутствующего навыка и фоновое повторное применение.
Сохранить порядок эпизодов одного студента, не блокируя остальных студентов той
же Kafka partition.

Готово, когда:

- неизвестный навык переводит inbox в `PendingCatalog`;
- появление навыка запускает успешное повторное применение;
- более поздний эпизод того же студента ждёт;
- другой студент продолжает обрабатываться;
- retry ограничен конфигурацией и не создаёт busy loop.

**Выполнено 2026-11-07.** Inbox выбирает только самый ранний незавершённый
эпизод для пары `ModuleKey + StudentId`, поэтому `PendingCatalog` удерживает
последующие эпизоды только этого студента. Очереди других студентов продолжают
обрабатываться. Изменение каталога в той же транзакции немедленно возвращает
связанные сообщения в `Received`; периодический retry остаётся резервным
механизмом, использует `NextRetryAt` и завершается безопасной ошибкой
`CatalogRetryLimitExceeded` после настроенного числа попыток. Сквозной тест на
Kafka/PostgreSQL проверяет изоляцию очередей, пробуждение и предел повторов.

### SPD-011 — Конкурентность и запоздавшие события

Добавить транзакционную PostgreSQL-блокировку на `StudentId + ModuleKey` и
детерминированный порядок `FinalizedAt`, затем `EpisodeId`.

Готово, когда:

- два экземпляра обработчика не применяют эпизод одновременно;
- параллельные события не теряют наблюдения;
- поздний эпизод вставляется в педагогически правильную позицию;
- блокировка одного студента не сериализует весь модуль;
- локальные process-locks не используются как единственная защита.

**Выполнено 2026-11-07.** Перед изменением истории обработчик получает
транзакционную PostgreSQL advisory-lock по хешу `ModuleKey + StudentId`; локальные
process-locks не используются. Очередь и чтение истории сортируются по настоящим
`FinalizedAt`, затем `EpisodeId`, а некорректный контракт безопасно попадает в
начало очереди для окончательного отклонения. PostgreSQL integration test
подтверждает сериализацию двух обработчиков одного студента, независимость другого
студента, отсутствие потери наблюдений и правильную позицию позднего эпизода.

настроек модуля.

### SPD-013 — Чистый BKT calculator

Готово, когда:

- формулы успеха, провала и перехода обучения соответствуют ТЗ;
- результат всегда находится в `[0; 1]`;
- для `ValidationRule` и `TaskTag` выбираются разные параметры;

Реализовано 2026-11-07. Чистый доменный калькулятор принимает предыдущую
вероятность, бинарный итог, источник наблюдения и параметры версии. Он выбирает
отдельные `Guess/Slip` для точного правила и навыка-тега, последовательно
применяет байесовское обновление и переход обучения, а результат ограничивает
диапазоном `[0; 1]`. Для недостижимых граничных наблюдений с нулевым знаменателем
зафиксирован детерминированный предел формулы. Unit-тесты покрывают успех,
провал, различие источников, граничные значения и последовательность наблюдений.

### SPD-014 — BKT-проекции и точечный пересчёт

## Итерация G — интеграция SQL Module

### SQLSPD-001 — Каталог навыков SQL Module

Реализовать CRUD системных и преподавательских навыков, soft-delete,

Готово, когда SQL Module является владельцем каталога, не создаёт дублирующие
строковые теги и публикует wire-контракт `SPD-004`.

### SQLSPD-002 — Навыки в снимке опубликованного задания

Связать каждое весовое правило с одним навыком, добавить теги и сохранять всё в

Готово, когда один `SkillId` встречается в снимке только один раз, изменение
разметки требует новой версии задания, а опубликованный эпизод закреплён за одним
снимком.

### SQLSPD-003 — Финализация учебного эпизода

Добавить явный жизненный цикл эпизода, heartbeat с трёхминутным окном, выбор

Готово, когда попытка сама не является наблюдением, каждый эпизод финализируется

### SQLSPD-004 — Outbox и Kafka publication

Публиковать каталог и `LearningEpisodeFinalized` через transactional outbox в
разные топики с правильными ключами.

Готово, когда commit предметной транзакции и запись outbox атомарны, повторная

### SQLSPD-005 — Клиент рекомендаций, fallback и smoke

Добавить типизированный HTTP-клиент EducationSPD. SQL Module формирует только
доступных кандидатов, задаёт короткий тайм-аут, применяет локальный fallback и
повторно проверяет выбранное задание.

Готово, когда пройден сквозной сценарий каталог → эпизод → BKT → ranking, а
недоступность EducationSPD не блокирует student API SQL Module.

## Параллельная работа агентов

После завершения `SPD-001` безопасно вести параллельно:

- ветка transport: `SPD-002` → `SPD-003`;
- ветка catalog: `SPD-004` + `SPD-005`, затем `SPD-006` → `SPD-007`;
- ветка mathematics: `SPD-012` → `SPD-013` и `SPD-016`;
- ветка episode persistence: `SPD-008` после фиксации Kafka DTO.

Нельзя параллельно без явного владельца общего файла:

- создавать несколько EF migrations поверх одного snapshot;
- одновременно менять `AppDbContext` и DI composition root;
- независимо менять Kafka DTO после `SPD-001`;
- независимо менять `ApiRoutes` и OpenAPI schemas одной функции.

Интеграционные задачи SQL Module начинаются после стабилизации соответствующего
wire-контракта, но не требуют завершения всей эксплуатационной итерации.
