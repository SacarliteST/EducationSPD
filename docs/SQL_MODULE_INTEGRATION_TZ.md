# Техническое задание: интеграция SQL Module с EducationSPD

## 1. Цель

Доработать SQL Module так, чтобы он:

- владел каталогом SQL-навыков и синхронизировал его с EducationSPD;
- закреплял навыки в неизменяемой опубликованной версии задания;
- формировал ровно одно наблюдение после финализации учебного эпизода, а не
  после каждой попытки;
- надёжно публиковал каталог и эпизоды через transactional outbox и Kafka;
- передавал EducationSPD только минимальные данные, необходимые для оценки
  навыков;
- запрашивал персональный порядок только среди заданий, которые SQL Module уже
  признал доступными студенту;
- продолжал работать при недоступности EducationSPD за счёт локального fallback.

SQL Module остаётся владельцем заданий, правил проверки, попыток, доступности и
жизненного цикла учебного эпизода. EducationSPD не должен получать SQL-текст,
балл, причину завершения, снимок задания или результаты выполнения запроса.

## 2. Ограничения задачи

В рамках этой доработки нельзя:

- переносить предметную логику SQL Module в EducationSPD;
- считать отдельную попытку наблюдением навыка;
- менять ранее опубликованный снимок задания;
- объединять успешные правила из разных попыток;
- позволять EducationSPD добавлять задания к набору доступных кандидатов;
- блокировать финализацию эпизода синхронным вызовом EducationSPD;
- публиковать Kafka-событие вне транзакционного outbox;
- дублировать публичные DTO вручную в SQL Module.

Интеграционные DTO следует получать из отдельных проектов
`EducationSPD.Contracts` и `EducationSPD.Kafka.Contracts`. Предпочтительный
способ межрепозиторной поставки — версионированные внутренние NuGet-пакеты. До
настройки package feed допустима временная project reference только в общей
локальной solution, но копирование исходников контрактов запрещено.

## 3. Общая конфигурация

Добавить типизированную конфигурацию через `IOptions`:

```yaml
EducationSpd:
  Enabled: true
  BaseUrl: http://education-spd
  ServiceKey: <secret>
  ModuleKey: sql
  RequestTimeoutMilliseconds: 1500
  Kafka:
    SkillCatalogTopic: learning.skill-catalog
    EpisodeFinalizedTopic: learning.episode-finalized
```

Требования:

- `ModuleKey` стабилен после появления первых событий; для SQL Module — `sql`;
- service key не имеет рабочего значения по умолчанию, не хранится в git и не
  попадает в логи;
- URL, тайм-ауты и имена топиков не зашиваются в код;
- некорректная обязательная конфигурация обнаруживается при старте;
- при `Enabled = false` каталог, эпизоды и задания продолжают работать локально,
  а интеграционные публикации и HTTP-вызовы отключены явно.

## 4. SQLSPD-001 — каталог навыков SQL Module

### 4.1. Модель

Добавить самостоятельную сущность навыка со следующими данными:

| Поле | Требование |
|---|---|
| `Id` | внутренний UUID |
| `SkillId` | стабильный внешний идентификатор, 1–100 символов |
| `Name` | обязательное название, до 300 символов |
| `Description` | необязательное описание, до 2000 символов |
| `Origin` | `System` или `TeacherDefined` |
| `IsDeleted` | признак мягкого удаления |
| `CreatedAt`, `UpdatedAt` | UTC |

`SkillId` содержит только строчные латинские буквы, цифры, `-`, `_`, `.` и
уникален внутри SQL Module. После создания `SkillId` не изменяется.

Системные навыки создаются разработчиками/сидинговым механизмом. Преподаватель
создаёт `TeacherDefined` навыки. Системный навык нельзя превратить в
преподавательский и наоборот.

### 4.2. CRUD и удаление

Добавить teacher/admin CRUD в стиле существующих controller endpoints SQL
Module. Нужны операции:

- получить страницу навыков с поиском и фильтром удаления;
- получить навык по идентификатору;
- создать преподавательский навык;
- изменить название и описание;
- выполнить мягкое удаление;
- восстановить мягко удалённый навык, если это поддерживается принятым UI.

Физическое удаление навыка запрещено. Все ссылки из снимков задания используют
`ON DELETE RESTRICT`. Редактирование не обнуляет накопленную историю; API должен
возвращать фронту явное предупреждение, что преподаватель отвечает за сохранение
педагогического смысла навыка.

### 4.3. Событие каталога

Создание, изменение, мягкое удаление и восстановление навыка в той же транзакции
создают outbox-сообщение `SkillCatalogChanged` версии 1:

```json
{
  "schemaVersion": 1,
  "eventId": "uuid",
  "moduleKey": "sql",
  "skillId": "join",
  "name": "Использование JOIN",
  "description": "Соединение данных нескольких таблиц",
  "origin": "System",
  "isDeleted": false,
  "occurredAt": "2026-11-08T12:00:00Z"
}
```

Использовать `KafkaContractJson.Serialize`, строковые enum и camelCase. Kafka key:

```text
sql:<skillId>
```

Повторная публикация одной outbox-записи сохраняет исходный `EventId` и payload.
Топик каталога настраивается с log compaction.

### 4.4. Проверки

- уникальность `SkillId` подтверждена доменными и PostgreSQL-тестами;
- редактирование не меняет идентичность;
- мягкое удаление не ломает старые снимки;
- новый снимок не может ссылаться на удалённый навык;
- предметное изменение и outbox-запись атомарны;
- повторная отправка использует тот же `EventId`.

## 5. SQLSPD-002 — навыки в опубликованном снимке задания

### 5.1. Связи

Каждое весовое правило опубликованной версии задания связано ровно с одним
навыком. Дополнительно снимок может содержать навыки-теги задания.

Инварианты одного снимка:

1. Каждое весовое правило имеет один `SkillId`.
2. Один навык встречается в снимке не более одного раза.
3. Навык используется либо правилом (`ValidationRule`), либо тегом (`TaskTag`),
   но не обоими способами одновременно.
4. Все навыки существуют, относятся к SQL Module и не удалены на момент
   публикации.
5. Изменение набора навыков или их связей требует выпуска новой версии задания.
6. Черновик можно редактировать, опубликованный снимок неизменяем.

Снимок хранит ссылку на навык и минимальные отображаемые данные навыка на момент
публикации, необходимые для исторического объяснения. Последующее переименование
навыка не изменяет старый снимок.

### 5.2. Публикация

Перед публикацией валидировать все перечисленные инварианты и возвращать
структурированный `422` по конкретным полям. Нельзя автоматически удалять
повторы или выбирать один из конфликтующих источников навыка.

Teacher details опубликованной версии должны позволять фронту увидеть:

- навык каждого правила;
- список навыков-тегов;
- источник будущего наблюдения;
- предупреждение о приблизительной природе навыков-тегов.

Student API не должен раскрывать внутренние параметры интеграции, но может
показывать педагогические названия навыков, если это будет отдельно принято UI.

## 6. SQLSPD-003 — жизненный цикл учебного эпизода

### 6.1. Определение и идентичность

Учебный эпизод — одна непрерывная работа студента над конкретным опубликованным
снимком задания. Он создаётся при начале выполнения и получает новый `EpisodeId`.
После финализации эпизод не возобновляется; повторный вход создаёт новый эпизод.

Эпизод должен хранить:

- `EpisodeId`, `StudentId`, `TaskId`, идентификатор снимка задания;
- время начала, последнего heartbeat и финализации;
- внутреннюю причину финализации;
- статус жизненного цикла;
- ссылку на выбранную итоговую попытку, если попытки были;
- признак, создаётся ли педагогическое наблюдение.

Причина финализации, балл и снимок не входят в Kafka-событие.

### 6.2. Heartbeat

Добавить student-safe heartbeat текущего эпизода. Повтор одного heartbeat
идемпотентен. После потери heartbeat студенту предоставляется ровно три минуты на
переподключение:

- возврат в течение окна продолжает тот же эпизод;
- после окна фоновая обработка финализирует эпизод как педагогический провал;
- поздний heartbeat финализированного эпизода не открывает его повторно;
- техническая ошибка фонового обработчика приводит к retry, а не к дублирующей
  финализации.

### 6.3. Причины финализации

| Причина | Наблюдение | Поведение |
|---|---|---|
| достигнуто 100 баллов | да | немедленно, текущая попытка |
| студент принял частичный результат | да | лучшая попытка |
| явный возврат на платформу/отказ | да, провал | немедленно |
| исчерпаны попытки | да, провал | автоматически |
| heartbeat отсутствует более 3 минут | да, провал | автоматически |
| истёк учебный лимит | да, провал | автоматически |
| техническое истечение сессии | нет | закрыть без события |
| сбой sandbox/инфраструктуры | нет | закрыть без события |
| административное закрытие | нет | закрыть без события |

Финализация выполняется идемпотентно. Конкурирующие причины не могут создать два
результата или два outbox-сообщения.

### 6.4. Выбор итоговой попытки

- при 100 баллах итоговой является текущая попытка;
- во всех остальных педагогических финализациях с попытками выбирается попытка с
  максимальным итоговым баллом;
- при равном балле выбирается более ранняя попытка, первой достигшая результата;
- результаты правил разных попыток не объединяются;
- `UserId`/`StudentId` берётся из доверенного JWT/session context, а не из body.

### 6.5. Формирование результатов навыков

Для итоговой попытки:

- каждое весовое правило создаёт один `SkillResult`;
- выполненное правило даёт `Succeeded`, невыполненное — `Failed`;
- `Source = ValidationRule`;
- вес правила и общий балл не влияют на бинарный outcome.

Для навыков-тегов:

- 100 баллов: все теги `Succeeded`;
- принятый частичный результат: теги не включаются в событие;
- явный отказ, уход по heartbeat, исчерпание попыток или учебный тайм-аут: все
  теги `Failed`;
- техническое закрытие: событие целиком отсутствует.

Если студент отказался до первой попытки, точные результаты правил отсутствуют,
но навыки-теги получают `Failed`. Событие должно содержать хотя бы один результат;
если у такого задания нет тегов и нет итоговой попытки, педагогическое событие
публиковать нельзя: этот случай должен быть явно зафиксирован в логах и покрыт
тестом как отсутствие проверяемого наблюдения.

## 7. SQLSPD-004 — transactional outbox и Kafka

### 7.1. Outbox

Использовать общий outbox SQL Module либо расширить существующий, не создавая
второй несовместимый механизм. Запись содержит как минимум:

- `EventId`;
- тип события и schema version;
- Kafka topic и key;
- неизменяемый JSON payload;
- время создания;
- статус, число попыток, время следующей попытки;
- безопасный код последней ошибки.

Финализация эпизода и создание `LearningEpisodeFinalized` фиксируются одной
транзакцией БД. Сбой Kafka после commit не отменяет эпизод; publisher повторяет
ту же outbox-запись с экспоненциальной задержкой.

### 7.2. Событие эпизода

```json
{
  "schemaVersion": 1,
  "eventId": "uuid",
  "episodeId": "uuid",
  "studentId": "uuid",
  "moduleKey": "sql",
  "taskId": "uuid",
  "finalizedAt": "2026-11-08T12:10:00Z",
  "skillResults": [
    {
      "skillId": "join",
      "source": "ValidationRule",
      "outcome": "Succeeded"
    }
  ]
}
```

Ограничения:

- `SchemaVersion = 1`;
- все UUID заполнены;
- `FinalizedAt` — UTC и равен времени финализации, а не публикации;
- 1–100 уникальных `SkillId`;
- один эпизод создаёт не более одного `EventId`;
- Kafka key — `sql:<studentId>`;
- сериализация только через `KafkaContractJson`;
- при наличии текущего W3C trace context publisher передаёт `traceparent` и
  `tracestate` в Kafka headers.

### 7.3. Наблюдаемость и безопасность

Логировать по-русски и структурированно:

- создание финализации и outbox-записи;
- успешную публикацию;
- технический retry и окончательную ошибку;
- дубликат команды финализации.

Не логировать SQL студента, payload события, service key, строки учебных данных и
персональные данные. `EventId`/`EpisodeId` помещать в logging scope.

## 8. SQLSPD-005 — клиент рекомендаций

### 8.1. Формирование кандидатов

До обращения к EducationSPD SQL Module самостоятельно отбирает задания, которые:

- опубликованы;
- доступны текущему студенту и платформенной сессии;
- соответствуют выбранной теме/курсу и остальным текущим фильтрам;
- имеют опубликованный снимок с навыками;
- не нарушают лимиты попыток и иные бизнес-ограничения модуля.

EducationSPD получает только этот набор и не является источником авторизации.

### 8.2. HTTP-запрос

```http
POST /api/v1/recommendations/rank
X-Service-Key: <secret>
Content-Type: application/json
```

```json
{
  "studentId": "uuid",
  "moduleKey": "sql",
  "candidates": [
    {
      "taskId": "uuid",
      "difficultyLevel": 3,
      "skills": [
        { "skillId": "join", "source": "ValidationRule" }
      ]
    }
  ]
}
```

Ограничения фактического API EducationSPD:

- 1–500 уникальных кандидатов;
- сложность 1–5;
- 1–100 уникальных навыков кандидата;
- `SkillId` должен существовать и не быть мягко удалён;
- `Source` — `ValidationRule` или `TaskTag`.

Ответ содержит `modelVersion` и каждый переданный `TaskId` ровно один раз с
`rank`, `rankScore` и структурированными причинами. SQL Module не должен
пересчитывать `rankScore` или менять порядок при успешном ответе.

### 8.3. Клиент и fallback

Клиент размещается в отдельном client/integration проекте SQL Module по принятой
архитектуре решения. Нужны:

- typed `HttpClient`;
- базовый URL и service key из `IOptions`;
- короткий настраиваемый тайм-аут;
- W3C trace propagation;
- cancellation token;
- безопасная обработка `401/403/422/5xx`, timeout и сетевой ошибки;
- отсутствие retry для `401/403/422`;
- ограниченный retry только для кратковременной сетевой ошибки, если он укладывается
  в общий timeout student-запроса.

При любой недоступности EducationSPD SQL Module возвращает локальный
детерминированный порядок: текущая бизнес-сортировка, затем `TaskId` как
tie-break. Студент не должен получать `500` только из-за СППР.

Перед открытием выбранного задания SQL Module повторно проверяет его
доступность. Рекомендация не является резервированием.

## 9. Миграции

Ожидаются миграции как минимум для:

- каталога навыков;
- связей навыков с правилами и тегами черновика/снимка;
- учебных эпизодов и heartbeat;
- идемпотентной финализации;
- outbox, если существующая таблица не поддерживает нужные события.

Миграции генерируются штатным EF-инструментом вне sandbox. Ручное редактирование
snapshot запрещено. `ON DELETE RESTRICT`, уникальные индексы и допустимые enum
закрепляются на уровне PostgreSQL, где это применимо.

## 10. Порядок реализации

1. Подключить версионированные contract assemblies и конфигурацию.
2. Реализовать каталог навыков и его outbox (`SQLSPD-001`).
3. Добавить навыки в черновик и опубликованный снимок (`SQLSPD-002`).
4. Реализовать эпизод, heartbeat и единственную финализацию (`SQLSPD-003`).
5. Подключить outbox publisher двух типов событий (`SQLSPD-004`).
6. Добавить HTTP-клиент ранжирования и fallback (`SQLSPD-005`).
7. Выполнить сквозной smoke с реальными PostgreSQL, Kafka и EducationSPD.

Каждый этап оформляется отдельным коммитом. Сгенерированные контракты/клиенты не
редактируются вручную.

## 11. Минимальные тесты приёмки

### Каталог и снимок

- CRUD преподавательского навыка и запрет смены `SkillId`;
- soft-delete, restore и `ON DELETE RESTRICT`;
- атомарность изменения навыка и outbox;
- повтор publisher сохраняет `EventId`;
- публикация задания отклоняет неизвестный/удалённый/повторный навык;
- изменение навыков опубликованного задания создаёт новый снимок.

### Эпизод

- попытка сама по себе не создаёт событие;
- 100 баллов финализируют текущую попытку один раз;
- частичная ручная финализация выбирает лучшую попытку;
- равный балл выбирает более раннюю попытку;
- результаты разных попыток не объединяются;
- явный отказ и учебный тайм-аут создают отрицательные теги;
- частичный принятый результат не содержит тегов;
- отказ без попытки не создаёт точные результаты правил;
- возврат heartbeat до трёх минут сохраняет эпизод;
- отсутствие heartbeat более трёх минут финализирует его один раз;
- техническое/административное закрытие не публикует наблюдение;
- два параллельных запроса финализации создают одну запись и один outbox event.

### Kafka и рекомендации

- реальные Kafka/Testcontainers получают оба v1-контракта;
- wire JSON проходит `KafkaContractJson.Deserialize` без преобразований;
- Kafka key соответствует контракту;
- после временного сбоя publisher повторяет тот же payload;
- HTTP-клиент передаёт service key и cancellation token;
- успешный ответ сохраняет весь набор кандидатов и порядок EducationSPD;
- timeout/5xx приводит к локальному fallback, а не к ошибке student API;
- неизвестное или уже закрытое задание повторно отбрасывается перед открытием;
- логи не содержат SQL, payload, service key и StudentId.

## 12. Definition of Done

- SQL Module является единственным владельцем навыков, снимков и эпизодов;
- событие создаётся только после окончательной педагогической финализации;
- каталог и эпизоды публикуются разными Kafka-контрактами и топиками;
- все публикации проходят через transactional outbox;
- повторная доставка идемпотентна;
- EducationSPD получает только минимальный контракт;
- недоступность EducationSPD не блокирует работу студента;
- миграции, форматирование, сборка, unit/integration tests проходят;
- сквозной сценарий `каталог → снимок → эпизод → Kafka → BKT → ranking` проверен;
- Swagger/клиент SQL Module обновлены штатным процессом, если появляются новые
  HTTP endpoints модуля;
- документация фронта обновлена без ручного изменения generated-кода.
