# Техническое задание на разработку EducationSPD

## 1. Общие сведения

### 1.1. Назначение системы

EducationSPD — самостоятельный backend-сервис платформы Scoodle, который:

- принимает итоговые результаты завершённых учебных эпизодов;
- накапливает историю наблюдений по навыкам студентов;
- оценивает предполагаемую степень освоения навыков;
- ранжирует переданный учебным модулем список доступных заданий;
- возвращает структурированное объяснение рекомендации.

Сервис не зависит от предметной области SQL. SQL Module является первым
интегрируемым модулем, но контракты и модель должны поддерживать другие учебные
модули без изменения ядра EducationSPD.

Основанием для требований является [CONCEPT.md](CONCEPT.md). При расхождении
между документами предметные решения определяются концепцией, а техническая
реализация — настоящим техническим заданием.

### 1.2. Цель первой версии

Первая версия должна сформировать полный минимальный контур:

```text
Каталог навыков модуля ──Kafka──► EducationSPD
Финализированный эпизод ─Kafka──► EducationSPD ──► BKT-проекция
Учебный модуль ──HTTP-кандидаты──► EducationSPD ──HTTP-рейтинг──► модуль
```

Результат первой версии должен позволить SQL Module передавать наблюдения и
получать персонализированный порядок собственных доступных заданий.

### 1.3. Термины

| Термин | Значение |
|---|---|
| Модуль | Предметный учебный сервис, например SQL Module |
| Навык | Стабильно идентифицируемая способность внутри одного модуля |
| Системный навык | Навык, созданный разработчиками модуля для точного правила проверки |
| Навык-тег | Переиспользуемый навык, назначаемый преподавателем заданию целиком |
| Учебный эпизод | Логическая работа студента над заданием до единственной финализации |
| Наблюдение | Итоговый бинарный результат одного навыка из финализированного эпизода |
| Проекция | Вычисленное из наблюдений текущее состояние навыка студента |
| BKT | Bayesian Knowledge Tracing — модель обновления вероятности освоения |
| МАИ | Метод анализа иерархий, используемый для получения весов ранжирования |

## 2. Границы ответственности

### 2.1. EducationSPD отвечает за

- хранение синхронизированного каталога навыков модулей;
- идемпотентный приём событий финализации эпизодов;
- проверку ссылочной целостности наблюдений относительно каталога навыков;
- хранение неизменяемой истории наблюдений;
- расчёт и восстановление BKT-проекций;
- ранжирование только переданных кандидатов;
- объяснение рассчитанного порядка;
- хранение версии и параметров математической модели;
- техническую наблюдаемость обработки событий.

### 2.2. Учебный модуль отвечает за

- CRUD своего каталога навыков;
- стабильность смысла идентификатора навыка;
- `OnDelete Restrict` и мягкое удаление используемых навыков;
- создание неизменяемого снимка опубликованной версии задания;
- привязку каждого весового правила к одному навыку;
- назначение навыков-тегов;
- недопущение повторения одного `SkillId` в рамках задания;
- определение итоговой попытки эпизода;
- формирование бинарных результатов навыков;
- классификацию педагогической и технической причины завершения;
- отправку ровно одного события на финализированный эпизод через outbox;
- отбор доступных студенту кандидатов;
- повторную проверку доступа перед открытием задания;
- fallback при недоступности EducationSPD;
- формирование локализованного student-safe текста рекомендации.

### 2.3. EducationSPD не должен

- принимать отдельные попытки как наблюдения;
- проверять предметное решение студента;
- пересчитывать результаты правил учебного модуля;
- хранить SQL, ответы, эталоны, DDL или другие предметные данные задания;
- хранить ФИО, email и роль студента;
- хранить курс, группу, практику или состав учебной группы;
- определять публикацию и доступность задания;
- самостоятельно находить или добавлять кандидатов;
- автоматически объединять навыки разных модулей;
- считать вероятность освоения объективным доказательством знания.

## 3. Функциональные требования

### 3.1. Каталог навыков

EducationSPD должен принимать определения навыков через Kafka. Навык уникально
определяется парой `ModuleKey + SkillId`.

Поддерживаются два происхождения навыка:

- `System`;
- `TeacherDefined`.

Редактирование названия и описания обновляет каталог, но не создаёт новый навык
и не сбрасывает историю. Удаление передаётся как `IsDeleted = true`. Kafka
tombstone в первой версии не используется.

Мягко удалённый навык:

- сохраняется в истории;
- может участвовать в обработке старого или запоздавшего эпизода;
- не должен использоваться модулем в новых публикациях;
- не удаляется физически EducationSPD.

### 3.2. Учебный эпизод

EducationSPD получает только окончательно финализированный эпизод. Событие
содержит все наблюдения этого эпизода и является неизменяемым.

Один эпизод формирует не более одного события. Повторное прохождение того же
задания создаёт новый `EpisodeId` и отдельное наблюдение.

Внутри одного события один `SkillId` может присутствовать только один раз.
Результат навыка бинарный:

- `Succeeded`;
- `Failed`.

Источник результата:

- `ValidationRule` — точное правило учебного модуля;
- `TaskTag` — косвенное педагогическое допущение.

EducationSPD не получает итоговый балл, причину завершения, вес правила,
предметное описание правила и снимок задания.

### 3.3. Правила формирования наблюдений в модуле

Интегрируемый модуль обязан соблюдать следующие правила:

1. При 100 баллах эпизод финализируется автоматически текущей попыткой.
2. При явном принятии частичного результата используется лучшая попытка.
3. При равном балле выбирается более ранняя попытка.
4. Результаты разных попыток не объединяются.
5. Исчерпание попыток считается неуспешной финализацией.
6. Явный отказ и уход со страницы считаются неуспешной финализацией.
7. После пропадания heartbeat предоставляется три минуты на переподключение.
8. Педагогический тайм-аут считается неуспешной финализацией.
9. Техническое или административное закрытие наблюдения не создаёт.
10. Для навыка правила передаётся фактический итог соответствующего правила.
11. Для навыка-тега передаётся `Succeeded` только при 100 баллах.
12. При принятом частичном результате навыки-теги не передаются.
13. При педагогическом провале все навыки-теги передаются как `Failed`.

EducationSPD доверяет итоговой классификации модуля и не пытается восстановить
её из косвенных полей.

## 4. Интеграция через Kafka

### 4.1. Топики

| Топик | Назначение | Ключ сообщения | Политика |
|---|---|---|---|
| `learning.skill-catalog` | Синхронизация навыков | `ModuleKey:SkillId` | log compaction |
| `learning.episode-finalized` | Итоговые эпизоды | `ModuleKey:StudentId` | обычный retention |

Названия должны настраиваться через `IOptions`, но указанные значения являются
значениями по умолчанию.

### 4.2. Версионирование wire-контрактов

Каждое сообщение должно содержать целое поле `SchemaVersion`. Первая версия
имеет значение `1`.

Consumer должен:

- принимать известную версию;
- отклонять неизвестную версию как неисправимое сообщение;
- сохранять безопасную причину ошибки;
- не пытаться молча интерпретировать новый контракт старой моделью.

Добавление необязательного поля допускается в пределах версии. Удаление,
переименование или изменение семантики поля требует новой версии.

### 4.3. Событие каталога навыков

```json
{
  "schemaVersion": 1,
  "eventId": "00000000-0000-0000-0000-000000000001",
  "moduleKey": "sql",
  "skillId": "join",
  "name": "Использование JOIN",
  "description": "Соединение данных нескольких таблиц",
  "origin": "System",
  "isDeleted": false,
  "occurredAt": "2026-11-06T12:00:00Z"
}
```

Требования к полям:

| Поле | Требование |
|---|---|
| `EventId` | обязательный UUID, идентификатор доставки |
| `ModuleKey` | обязательный, 1–100 символов, нижний регистр, цифры и `-` |
| `SkillId` | обязательный, 1–100 символов, нижний регистр, цифры, `-`, `_`, `.` |
| `Name` | обязательный, 1–300 символов |
| `Description` | необязательный, не более 2000 символов |
| `Origin` | `System` или `TeacherDefined` |
| `IsDeleted` | обязательный boolean |
| `OccurredAt` | обязательный UTC timestamp |

Повторный `EventId` должен завершаться без повторного применения. Более старое
событие каталога не должно перезаписывать более новое состояние. Порядок
определяется по `OccurredAt`, при равенстве — по `EventId`.

### 4.4. Событие финализации эпизода

```json
{
  "schemaVersion": 1,
  "eventId": "00000000-0000-0000-0000-000000000002",
  "episodeId": "00000000-0000-0000-0000-000000000003",
  "studentId": "00000000-0000-0000-0000-000000000004",
  "moduleKey": "sql",
  "taskId": "00000000-0000-0000-0000-000000000005",
  "finalizedAt": "2026-11-06T12:10:00Z",
  "skillResults": [
    {
      "skillId": "join",
      "source": "ValidationRule",
      "outcome": "Succeeded"
    }
  ]
}
```

Требования:

- все UUID обязательны и не равны `Guid.Empty`;
- `FinalizedAt` должен содержать UTC-время;
- `SkillResults` содержит от 1 до 100 элементов;
- `SkillId` уникален внутри события;
- `Source` принимает `ValidationRule` или `TaskTag`;
- `Outcome` принимает `Succeeded` или `Failed`;
- неизвестные enum-значения не принимаются.

### 4.5. Inbox и подтверждение Kafka offset

Consumer сначала сохраняет входящее сообщение в PostgreSQL, затем подтверждает
Kafka offset. Потеря процесса после сохранения и до подтверждения приводит к
повторной доставке, которая устраняется по `EventId`.

Состояния inbox:

- `Received` — сообщение сохранено;
- `PendingCatalog` — отсутствует определение одного или нескольких навыков;
- `Applied` — наблюдения и проекции успешно обновлены;
- `Failed` — сообщение неисправимо.

Транспортный consumer не должен удерживать Kafka partition во время длительного
ожидания каталога. Сообщение переводится в `PendingCatalog`, а фоновый обработчик
повторяет применение после обновления каталога.

Ожидающее событие блокирует применение более поздних эпизодов только для той же
пары `ModuleKey + StudentId`. Другие студенты, включая находящихся в той же
Kafka partition, продолжают обрабатываться.

### 4.6. Идемпотентность и конфликт

Должны действовать два независимых ограничения:

- уникальный `EventId` защищает от повторной доставки;
- уникальная пара `ModuleKey + EpisodeId` защищает от бизнес-дубликата.

Если повторно получены те же `EventId` и payload, обработка считается успешной.
Если для существующего `ModuleKey + EpisodeId` пришёл другой `EventId`, сообщение
переводится в `Failed` с кодом `EpisodeConflict`; существующий эпизод и проекции
не перезаписываются.

Исправление и компенсация уже принятого эпизода в первой версии не поддерживаются.

## 5. Математическая модель BKT

### 5.1. Состояние

Состояние хранится отдельно для каждой тройки:

```text
StudentId + ModuleKey + SkillId
```

Главное значение — `MasteryProbability` в диапазоне `[0; 1]`.

### 5.2. Параметры

Версия модели содержит:

- `P(L0)` — начальная вероятность освоения;
- `P(T)` — вероятность обучения после учебной возможности;
- `P(G)` и `P(S)` для `ValidationRule`;
- `P(G)` и `P(S)` для `TaskTag`.

Все значения должны находиться в диапазоне `[0; 1]`. Дополнительно:

- `P(G) + P(S) < 1` для каждого источника;
- параметры точного правила должны быть не менее надёжными, чем параметры тега:
  `RuleGuess <= TagGuess` и `RuleSlip <= TagSlip`.

Стартовые параметры первой версии:

| Параметр | Значение |
|---|---:|
| `P(L0)` | 0.20 |
| `P(T)` | 0.10 |
| `ValidationRule P(G)` | 0.10 |
| `ValidationRule P(S)` | 0.10 |
| `TaskTag P(G)` | 0.25 |
| `TaskTag P(S)` | 0.25 |

Значения являются исходной инженерной гипотезой, а не научно откалиброванными
показателями. Это должно быть явно отражено в пользовательской документации.

### 5.3. Формулы обновления

Для предыдущей вероятности `L` при успешном наблюдении:

```text
PosteriorSuccess =
    L * (1 - Slip) /
    (L * (1 - Slip) + (1 - L) * Guess)
```

При неуспешном наблюдении:

```text
PosteriorFailure =
    L * Slip /
    (L * Slip + (1 - L) * (1 - Guess))
```

После учёта результата применяется переход обучения:

```text
NextMastery = Posterior + (1 - Posterior) * Learn
```

Результат ограничивается диапазоном `[0; 1]`. Вычисления выполняются в `decimal`
с достаточной точностью хранения, а наружу значение отдаётся с точностью не
хуже четырёх знаков после запятой.

### 5.4. Порядок наблюдений

Наблюдения одного навыка применяются в порядке:

1. `FinalizedAt` по возрастанию;
2. `EpisodeId` по возрастанию при равном времени.

Порядок доставки Kafka не является педагогическим порядком.

Запоздавшее наблюдение вставляется в правильное место, после чего проекция
затронутого навыка пересчитывается из исходной истории. Обновление выполняется
последовательно для одного `StudentId + ModuleKey`; обработка разных студентов
может выполняться параллельно.

Для исключения гонок реализация должна использовать транзакционную блокировку
PostgreSQL на пару `StudentId + ModuleKey` либо эквивалентный механизм с теми же
гарантиями. Локальная блокировка процесса недостаточна, поскольку сервис может
работать в нескольких экземплярах.

### 5.5. Версия модели и полный пересчёт

Параметры модели сохраняются как версионируемая конфигурация. Одновременно
активна одна версия.

Активация новой версии запускает фоновое построение новых проекций из исходных
наблюдений. До полного завершения используются проекции последней целостной
версии. Частично пересчитанная версия не должна становиться доступной API.

Пересчёт должен быть возобновляемым и не должен изменять исходные наблюдения.

## 6. Ранжирование заданий

### 6.1. Входной набор

EducationSPD получает уже отфильтрованный одним модулем список. Один запрос не
может содержать задания разных модулей.

Кандидат содержит:

```text
TaskId
DifficultyLevel
Skills[]
  SkillId
  Source
```

Ограничения:

- от 1 до 500 кандидатов;
- `TaskId` уникален в запросе;
- `DifficultyLevel` от 1 до 5;
- от 1 до 100 навыков в кандидате;
- `SkillId` уникален в кандидате;
- навык должен существовать в каталоге указанного модуля;
- мягко удалённый навык допустим только для исторической обработки, но не для
  нового запроса ранжирования.

### 6.2. Критерии

Все критерии нормализованы в диапазон `[0; 1]`.

#### Дефицит навыков

```text
SkillDeficit = 1 - MasteryProbability
KnowledgeDeficit = Average(SkillDeficit)
```

Если персональной проекции нет, используется `P(L0)` активной модели.

#### Соответствие сложности

| Среднее освоение навыков | Целевая сложность |
|---:|---:|
| `< 0.30` | 1 |
| `0.30–0.49` | 2 |
| `0.50–0.69` | 3 |
| `0.70–0.84` | 4 |
| `>= 0.85` | 5 |

```text
DifficultyFit = 1 - Abs(CandidateDifficulty - TargetDifficulty) / 4
```

#### Новизна

```text
Novelty = 1 / (1 + FinalizedEpisodeCountForTask)
```

Учитываются все принятые финализированные эпизоды студента по этому заданию,
независимо от результата.

#### Диагностическая ценность

```text
DiagnosticValue = ValidationRuleSkillCount / AllCandidateSkillCount
```

### 6.3. МАИ и итоговый балл

Базовая матрица попарных сравнений:

| Критерий | Дефицит | Сложность | Новизна | Диагностичность |
|---|---:|---:|---:|---:|
| Дефицит | 1 | 3 | 5 | 7 |
| Сложность | 1/3 | 1 | 3 | 4 |
| Новизна | 1/5 | 1/3 | 1 | 2 |
| Диагностичность | 1/7 | 1/4 | 1/2 | 1 |

Веса рассчитываются из матрицы единым детерминированным алгоритмом и
нормализуются до суммы 1. Допускается метод геометрических средних строк.

Перед активацией матрицы проверяются:

- положительность;
- единицы на диагонали;
- взаимная обратность элементов с допустимой погрешностью;
- `CR <= 0.10`.

Базовые приблизительные веса:

| Критерий | Вес |
|---|---:|
| Дефицит навыков | 0.57 |
| Соответствие сложности | 0.25 |
| Новизна | 0.11 |
| Диагностическая ценность | 0.07 |

```text
RankScore =
    KnowledgeDeficitWeight * KnowledgeDeficit +
    DifficultyFitWeight * DifficultyFit +
    NoveltyWeight * Novelty +
    DiagnosticValueWeight * DiagnosticValue
```

Сортировка: `RankScore DESC`, затем `TaskId ASC`. Одинаковый вход при неизменных
проекциях и конфигурации должен давать одинаковый результат.

### 6.4. Объяснение

Для каждого кандидата возвращаются вклады критериев и связанные навыки.
Поддерживаемые коды:

- `TargetsWeakSkills`;
- `DifficultyMatchesCurrentLevel`;
- `TaskIsNewForStudent`;
- `ProvidesPreciseAssessment`.

EducationSPD не формирует педагогические утверждения вроде «навык не освоен».
Модуль локализует и смягчает формулировку, используя вероятностный характер
оценки.

## 7. HTTP API

### 7.1. Общие требования

- Базовый префикс: `/api/v1`.
- Все прикладные endpoint доступны только доверенным сервисам платформы.
- Сервисная аутентификация первой версии: заголовок `X-Service-Key`.
- Ключ хранится в secret/environment configuration и не попадает в репозиторий,
  логи или ProblemDetails.
- Проверка ключа выполняется constant-time сравнением.
- Все endpoint поддерживают `CancellationToken`.
- Все публичные DTO и endpoint документируются в OpenAPI на русском языке.
- Ошибки возвращаются в формате `ProblemDetails`.
- Ошибки полей возвращаются как `422 ValidationProblemDetails`.
- Необработанная ошибка возвращает безопасный `500` без stack trace и сырых
  сообщений инфраструктуры.

### 7.2. Получение состояний навыков

```http
GET /api/v1/modules/{moduleKey}/students/{studentId}/skills
```

Query-параметры:

- `includeDeleted=false` — включать ли мягко удалённые навыки;
- `offset=0`;
- `limit=100`, диапазон 1–500.

Ответ `200`:

```json
{
  "count": 1,
  "offset": 0,
  "limit": 100,
  "modelVersion": 1,
  "items": [
    {
      "skillId": "join",
      "name": "Использование JOIN",
      "description": "Соединение данных нескольких таблиц",
      "origin": "System",
      "isDeleted": false,
      "masteryProbability": 0.7342,
      "observationsCount": 4,
      "lastObservedAt": "2026-11-06T12:10:00Z"
    }
  ]
}
```

Навык без наблюдений может быть включён в ответ с `P(L0)`, нулевым количеством и
`lastObservedAt = null`.

Ответы: `200`, `401`, `403`, `422`, `500`.

### 7.3. Ранжирование кандидатов

```http
POST /api/v1/recommendations/rank
```

Запрос:

```json
{
  "studentId": "00000000-0000-0000-0000-000000000004",
  "moduleKey": "sql",
  "candidates": [
    {
      "taskId": "00000000-0000-0000-0000-000000000005",
      "difficultyLevel": 2,
      "skills": [
        {
          "skillId": "join",
          "source": "ValidationRule"
        }
      ]
    }
  ]
}
```

Ответ `200`:

```json
{
  "modelVersion": 1,
  "items": [
    {
      "taskId": "00000000-0000-0000-0000-000000000005",
      "rank": 1,
      "rankScore": 0.8123,
      "reasons": [
        {
          "code": "TargetsWeakSkills",
          "contribution": 0.4210,
          "skillIds": ["join"]
        }
      ]
    }
  ]
}
```

Ответ содержит каждый входной кандидат ровно один раз. EducationSPD не добавляет
собственные `TaskId`.

Ответы: `200`, `401`, `403`, `422`, `500`.

### 7.4. Health endpoints

Должны существовать:

- `/health/live` — процесс работает;
- `/health/ready` — PostgreSQL доступен, миграции применены, Kafka consumer
  инициализирован.

Недоступность Kafka broker после успешного старта не должна останавливать HTTP
процесс, но должна переводить readiness в нездоровое состояние.

### 7.5. Коды прикладных ошибок

Минимальный набор:

| Код | HTTP | Условие |
|---|---:|---|
| `Authentication.Required` | 401 | отсутствует сервисный ключ |
| `Authentication.InvalidServiceKey` | 403 | неверный сервисный ключ |
| `Validation.Failed` | 422 | ошибки полей запроса |
| `Module.NotFound` | 422 | модуль отсутствует в каталоге |
| `Skill.NotFound` | 422 | навык кандидата отсутствует |
| `Skill.Deleted` | 422 | удалённый навык передан для ранжирования |
| `Recommendation.MixedModules` | 422 | нарушена модульная граница |
| `Model.ConfigurationInvalid` | 500 | активная конфигурация некорректна |

## 9. Архитектура реализации

### 9.1. Слои

| Проект | Содержимое |
|---|---|
| `EducationSPD.Domain` | сущности, enum и доменные инварианты |
| `EducationSPD.Application` | сценарии, интерфейсы хранилищ, BKT и ranking orchestration |
| `EducationSPD.Contracts` | HTTP DTO и `ApiRoutes` |
| `EducationSPD.Kafka.Contracts` | Версионированные Kafka DTO и единая JSON-сериализация без зависимости от Kafka SDK |
| `EducationSPD.Infrastructure` | EF Core, Kafka consumers, background workers, repositories |
| `EducationSPD.Web` | ASP.NET Core Controllers, validators, mappings, auth и регистрация HTTP-слоя |
| `EducationSPD.Host` | Точка входа, composition root и настройка HTTP-конвейера |
| `EducationSPD.Tests` | HTTP и интеграционные тесты PostgreSQL/Kafka |

Domain и Application не должны зависеть от Web или Infrastructure. Kafka и EF
не должны проникать в доменные типы.

HTTP API реализуется через классы-наследники `ControllerBase` с атрибутом
`[ApiController]`. Маршруты берутся из `EducationSPD.Contracts.ApiRoutes`.
Приложение регистрирует `AddControllers()` и вызывает `MapControllers()`.
Minimal API (`MapGet`, `MapPost`, `MapGroup` и endpoint groups) для новых функций
не используется. Контроллер выполняет только транспортную валидацию, mapping и
вызов одного application-сценария; бизнес-логика и EF-запросы в нём запрещены.

### 9.2. Группировка по функциям

Предлагаемые функции:

- `Skills`;
- `LearningEpisodes`;
- `KnowledgeStates`;
- `Recommendations`;
- `ModelConfiguration`;
- `Inbox`.

Один тип размещается в одном файле. Не создавать универсальные `Manager`,
`Helper` и generic-репозитории, если они скрывают предметный сценарий.

### 9.3. Транзакционность

Применение episode-события должно быть одной транзакцией:

1. захватить блокировку студента и модуля;
2. проверить inbox и бизнес-идемпотентность;
3. проверить наличие навыков;
4. сохранить эпизод и наблюдения;
5. пересчитать затронутые проекции;
6. изменить inbox на `Applied`;
7. зафиксировать транзакцию.

Kafka offset подтверждается после commit БД.

### 9.4. Кэш рекомендаций

Кэш является необязательной оптимизацией. Первая реализация может работать без
него. При добавлении кэш должен учитывать:

- `StudentId`;
- `ModuleKey`;
- версию модели;
- отпечаток упорядоченного набора кандидатов;
- текущую версию проекций студента.

Новое наблюдение инвалидирует кэш студента внутри модуля. Ошибка кэша не должна
блокировать расчёт.

## 10. Безопасность и приватность

- HTTP API не публикуется напрямую пользователю через внешний gateway.
- Доверять `StudentId` разрешено только аутентифицированному сервису.
- Kafka ACL должны разрешать учебным модулям запись только в согласованные
  топики, EducationSPD — чтение этих топиков.
- В логах запрещены service key, полный payload эпизода, персональные данные и
  stack trace в HTTP-ответе.
- UUID студента допускается в структурированных технических логах только там,
  где он нужен для диагностики; предпочтительно логировать его хеш или
  корреляционный идентификатор.
- Сервис хранит минимальный набор данных и не обогащает его через Identity.
- Все timestamps сохраняются в UTC.

## 11. Логирование, метрики и диагностика

### 11.1. Логи

Логи должны быть структурированными и содержать русский шаблон сообщения.

Обязательные события:

- consumer запущен и остановлен;
- событие каталога применено или проигнорировано как повтор;
- эпизод применён;
- эпизод ожидает каталог;
- обнаружен конфликт эпизода;
- сообщение окончательно отклонено;
- начат и завершён пересчёт версии модели;
- HTTP-ранжирование завершено с количеством кандидатов и временем;
- внешний вызов отклонён из-за аутентификации.

Не логировать каждый успешный BKT-шаг отдельно на уровне Information.

### 11.2. Метрики

Минимальный набор:

- `educationspd_kafka_messages_total{topic,status}`;
- `educationspd_inbox_pending_catalog`;
- `educationspd_inbox_failed_total{error_code}`;
- `educationspd_episode_apply_duration_seconds`;
- `educationspd_projection_recalculations_total{status}`;
- `educationspd_recommendation_requests_total{status}`;
- `educationspd_recommendation_duration_seconds`;
- `educationspd_recommendation_candidates`;
- `educationspd_model_recalculation_progress`.

### 11.3. Корреляция

HTTP должен поддерживать W3C trace context. Для Kafka producer/consumer должны
передаваться trace headers, если они присутствуют. `EventId` и `EpisodeId`
добавляются в scope обработки, но не включаются в текст каждой вручную созданной
строки.

## 12. Отказоустойчивость

- Ошибка PostgreSQL или Kafka приводит к retry с ограниченной экспоненциальной
  задержкой.
- Ошибки контракта и бизнес-конфликты не повторяются бесконечно.
- После настраиваемого количества технических повторов inbox получает `Failed`,
  сообщение и причина сохраняются для диагностики.
- В первой версии автоматическое исправление `Failed` не требуется, но должна
  существовать возможность безопасного повторного запуска операционной командой.
- Падение EducationSPD не должно блокировать открытие учебного модуля: модуль
  использует собственный fallback.
- Ранжирование не создаёт резервирование и не изменяет знания.
- Модуль обязан повторно проверить задание после получения рекомендации.

## 13. Конфигурация

Все параметры передаются через типизированные `IOptions` и валидируются при
старте:

```text
ConnectionStrings:Postgres
Kafka:BootstrapServers
Kafka:ConsumerGroup
Kafka:Topics:SkillCatalog
Kafka:Topics:EpisodeFinalized
Kafka:Retry:MaxAttempts
Kafka:Retry:InitialDelay
ServiceAuthentication:ServiceKey
Model:InitialParameters:...
Model:AhpMatrix:...
Inbox:PendingCatalogRetryInterval
Inbox:BatchSize
Recalculation:BatchSize
```

Секреты не должны иметь рабочие значения по умолчанию. Некорректная обязательная
конфигурация останавливает запуск с понятным сообщением без значения секрета.

## 14. Производительность

Целевые показатели первой версии на тестовом VPS при доступной БД:

- ранжирование 100 кандидатов: p95 не более 300 мс;
- ранжирование 500 кандидатов: p95 не более 1000 мс;
- применение эпизода до 100 навыков: p95 не более 500 мс без учёта Kafka lag;
- HTTP API не выполняет N+1-запросы по кандидатам;
- чтение использует `AsNoTracking`;
- пагинация имеет стабильную сортировку;
- все операции поддерживают отмену.

Показатели являются целевыми и подтверждаются отдельным измерением после
функциональной готовности, а не нестабильными тайминговыми тестами CI.

## 15. Тестирование

### 15.1. Модульные тесты

Проверить:

- BKT для успеха и провала;
- разные `Guess/Slip` для правила и тега;
- граничные параметры модели;
- последовательность нескольких наблюдений;
- детерминированный порядок при равном `FinalizedAt`;
- все четыре критерия ранжирования;
- границы целевой сложности;
- расчёт весов МАИ;
- отклонение несогласованной матрицы;
- детерминированную сортировку при равном `RankScore`;
- холодный старт через `P(L0)`.

### 15.2. Интеграционные тесты Kafka и PostgreSQL

Проверить:

- создание и обновление навыка;
- мягкое удаление навыка;
- старое событие каталога не перезаписывает новое;
- повторный `EventId` не дублирует изменения;
- эпизод сохраняет все результаты;
- повторная доставка не создаёт второй эпизод;
- другой `EventId` для того же эпизода создаёт конфликт;
- неизвестный навык переводит событие в `PendingCatalog`;
- появление навыка разблокирует событие;
- ожидание одного студента не блокирует другого;
- позднее событие вызывает хронологический пересчёт;
- параллельные события одного студента не теряют наблюдения;
- параллельные экземпляры обработчика соблюдают блокировку;
- неисправимое сообщение получает `Failed`;
- offset подтверждается только после сохранения inbox.

### 15.3. HTTP-интеграционные тесты

Проверить:

- отсутствие ключа возвращает `401`;
- неверный ключ возвращает `403`;
- корректный сервис получает `200`;
- ошибки DTO возвращаются единым `422` со словарём полей;
- состояния навыков принадлежат только указанному студенту и модулю;
- удалённые навыки по умолчанию скрыты;
- холодный старт возвращает `P(L0)`;
- ranking возвращает только входные `TaskId`;
- каждый кандидат возвращается один раз;
- неизвестный и удалённый навык отклоняются;
- смешение модулей невозможно;
- рейтинг и причины соответствуют формулам;
- повторный запрос детерминирован;
- OpenAPI объявляет все ответы и enum;
- `500` не раскрывает внутреннее исключение.

Тесты выполняются с PostgreSQL Testcontainers. Kafka-интеграцию следует
проверять Testcontainers либо совместимым реальным broker, не in-memory mock.

## 17. Критерии приёмки MVP

MVP считается готовым, если одновременно выполнены условия:

1. SQL Module может синхронизировать навык с EducationSPD.
2. Финализированный эпизод доставляется через outbox и Kafka.
3. Повторная доставка не создаёт повторного наблюдения.
4. Неизвестный навык не приводит к потере события.
5. Позднее событие даёт тот же результат, что исходная хронологическая доставка.
6. Для точного правила и тега применяются разные параметры достоверности.
7. Состояние одного студента не влияет на состояние другого.
8. Состояния одноимённых навыков разных модулей не смешиваются.
9. Ranking принимает только кандидатов одного модуля.
10. Ответ содержит исключительно переданные задания.
11. Порядок детерминирован и объяснён вкладами критериев.
12. Недоступность EducationSPD не блокирует работу SQL Module.
13. В API и логах отсутствуют предметные решения и лишние персональные данные.
14. Миграции, сборка и тесты проходят штатно.
15. OpenAPI соответствует фактическим контрактам.

## 18. Проверки перед завершением реализации

В репозитории EducationSPD выполнить:

```powershell
dotnet format EducationSPD.sln
dotnet build EducationSPD.sln
dotnet test EducationSPD.sln
```

Генерацию миграций и OpenAPI выполнять вне sandbox согласно репозиторному skill.
Не редактировать сгенерированные файлы вручную.

## 19. Явные ограничения первой версии

В MVP не входят:

- автоматическая калибровка BKT по историческим данным;
- исправление и компенсация применённого эпизода;
- объединение навыков разных модулей;
- межмодульное ранжирование заданий;
- сравнение студентов и построение рейтинга группы;
- прогноз оценки по курсу;
- генерация учебных заданий;
- самостоятельный отбор доступных заданий EducationSPD;
- хранение полного снимка задания;
- анализ отдельных попыток или действий в редакторе;
- пользовательский frontend EducationSPD.

Расширение этих границ требует отдельного изменения концепции и wire-контрактов.
